# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## Kiosk v2.0 — модульная система управления информационными киосками и экранами

**Версия ТЗ:** 1.0  
**Статус:** готовая редакция для согласования  
**Исходный проект:** Kiosk v1.0.0 MVP  
**Ветка разработки:** `v2`  
**Базовый Git-тег:** `v1.0.0-mvp`

---

# 1. Назначение системы

Разработать на основе существующего Kiosk MVP единую модульную систему управления информационными киосками, телевизорами и другими экранами в локальной сети организации.

Система должна позволять устанавливать устройства, объединять их в группы, управлять содержимым, публиковать изменения, контролировать синхронизацию и восстанавливать работоспособность после сбоев.

Основные принципы:

1. **Автономность.** Интернет не требуется для повседневной работы, запуска, управления, синхронизации и восстановления.
2. **Надёжность.** Подготовленные устройства продолжают показывать сохранённое содержимое при отказе сервера или сети.
3. **Модульность.** Необязательные функциональные модули не должны нарушать работу ядра.
4. **Сохранность данных.** Изменения фиксируются с понятным уровнем гарантий; предусматриваются резервирование и восстановление.
5. **Совместимость.** Существующие функции и данные сохраняются при переходе на новые версии в рамках утверждённого пути обновления.
6. **Простота.** Основные операции доступны пользователю без навыков программирования.
7. **Контролируемость.** Состояние устройств, публикаций, обновлений и ошибок должно быть понятно оператору.
8. **Безопасность.** Управление устройствами и содержимым выполняется только авторизованными участниками.

# 2. Исходный проект и ограничения разработки

Основой является существующее приложение Kiosk, в котором уже реализованы:

- Управление событиями.
- Работа с тегами.
- Настройки приложения.
- Загрузка и обработка изображений.
- Авторизация.
- Переводы интерфейса.
- Публичные режимы отображения.
- Проверка обновления содержимого.
- Хранение данных в SQLite.
- Запуск с Waitress.
- Конфигурация сборки через PyInstaller.

Используемые технологии: Python, Flask, SQLite, HTML, CSS, JavaScript, Pillow, Waitress, PyInstaller.

Требования:

1. Сохранить Git-тег `v1.0.0-mvp` и историю MVP без изменений.
2. Продолжать разработку в ветке `v2`.
3. Повторно использовать существующие проверенные компоненты.
4. Не переписывать работающий функционал без технической необходимости.
5. Не удалять данные пользователя при переходе на новую версию.
6. Изменение технологического стека допускать только по обоснованному архитектурному решению и после необходимых испытаний.
7. Не считать предыдущие smoke-тесты подтверждением совместимости с физическими Android TV, длительной стабильности или установки на чистый компьютер.

Разработка версии 2 не означает автоматического разрешения на добавление любых новых функциональных модулей.

# 3. Поддерживаемые платформы и устройства

## 3.1. Основные типы устройств

Система должна поддерживать на подтверждённой испытаниями матрице оборудования:

- Компьютеры под Windows.
- Сенсорные информационные киоски.
- Экраны без сенсорного управления.
- Android TV и совместимые устройства.
- Выделенные локальные серверы.

Windows 10 рассматривается как предварительная целевая система.

Для Android TV желательна работа на устройствах примерно с 2 ГБ оперативной памяти и 32 ГБ общего хранилища или меньшими ресурсами.

Окончательные требования определяются испытаниями конкретных моделей, версий ОС, процессоров, доступной оперативной памяти и свободного пространства.

**Важно:** Windows EXE не считается совместимым с Android. Для разных платформ допускаются отдельные установочные пакеты при сохранении единого пользовательского продукта и совместимого протокола взаимодействия.

## 3.2. Количество устройств

Целевой масштаб системы — **до 100 зарегистрированных устройств суммарно во всех группах одной установки**.

Это не ограничение в 100 устройств на каждую группу.

При испытаниях необходимо учитывать:

- Число групп.
- Распределение устройств по группам.
- Количество одновременно подключённых клиентов.
- Количество активных административных сессий.
- Объём изображений и видео.
- Количество событий.
- Интенсивность изменений.
- Характеристики сети и серверного оборудования.

Поддержка 100 устройств считается подтверждённой только после соответствующих нагрузочных испытаний.

# 4. Архитектура системы

Система состоит из логически разделённых компонентов.

## 4.1. Core — ядро

Ядро отвечает за:

- Постоянную идентификацию устройств.
- Управление группами.
- Аутентификацию и права доступа.
- Конфигурацию.
- Контролируемые операции хранения данных.
- Синхронизацию.
- Координацию репликации.
- Жизненный цикл модулей.
- Диагностику.
- Координацию обновлений.
- Управление состоянием восстановления.

Ядро должно оставаться минимальным и не зависеть от необязательных функций.

## 4.2. Launcher — программа запуска

Предоставляет интерфейс первоначальной настройки, запуска, остановки, диагностики, контроля состояния и обслуживания.

## 4.3. Display Client — клиент отображения

Обеспечивает:

- Загрузку содержимого.
- Локальное хранение опубликованных данных.
- Отображение событий и медиаматериалов.
- Сенсорную и несенсорную навигацию.
- Адаптацию под параметры экрана.
- Автономную работу.
- Безопасное переключение опубликованных версий.

## 4.4. Feature Modules — функциональные модули

Предоставляют отдельные функции через определённые интерфейсы ядра.

Первый эталонный модуль — **«События» (Events)**.

## 4.5. Updater/Recovery — обновление и восстановление

Отдельный компонент, который:

- Проверяет обновления.
- Подготавливает их установку.
- Управляет безопасной остановкой процессов.
- Выполняет необходимые миграции.
- Проверяет результат запуска.
- Предоставляет совместимые сценарии восстановления.

Он не должен полностью зависеть от исправности обновляемого процесса.

Внутреннее разделение на процессы допускается, но установка и повседневное использование должны выглядеть как работа с одним программным продуктом.

# 5. Установка и первоначальный запуск

## 5.1. Мастер настройки

При первоначальном запуске предложить:

1. Название устройства.
2. Поиск существующих групп.
3. Создание группы или подключение к существующей.
4. Выбор допустимой роли устройства.
5. Ориентацию экрана.
6. Режим отображения.
7. Параметры автоматического запуска.
8. Первоначальную настройку администратора.

Присоединение к существующей группе требует разрешения уполномоченного администратора или прохождения предусмотренной процедуры сопряжения.

Автоматически включать устройство в обнаруженную группу запрещено.

Если сетевое обнаружение невозможно, предусмотреть ручной ввод адреса.

## 5.2. Главное окно Launcher

Отображать:

- Название устройства и его роль.
- Название группы.
- Версии приложения, ядра и модулей.
- Состояние запуска.
- Локальный и сетевые адреса.
- Количество доступных, устаревших по связи и недоступных устройств.
- Последнюю успешную синхронизацию.
- Состояние репликации.
- Состояние обновления и восстановления.
- Предупреждения о недостатке памяти, дискового пространства и других ресурсов.

Предоставить действия:

- Запуск.
- Корректная остановка.
- Настройки.
- Открытие отображения.
- Открытие администрирования.
- Экспорт диагностики.
- Вход в восстановление.

Остановка сервера должна предупреждать о последствиях. Если безопасная передача роли доступна, предложить её.

Незавершённые операции записи должны корректно завершаться либо безопасно прерываться.

## 5.3. Автоматический запуск

Сохранять последнюю корректную конфигурацию.

После включения или перезапуска устройства восстанавливать предыдущие настройки и режим, если это поддерживается конкретной платформой.

Отдельно проверять:

- Автозапуск после входа пользователя в ОС.
- Возможность автономного запуска без ручного входа.
- Полноэкранный режим.
- Выход в режим обслуживания.
- Восстановление работы после аварийной остановки.

Не изменять параметры входа ОС, питания или прошивки без разрешения оператора.

## 5.4. Разделение файлов

Хранить отдельно:

- Исполняемые компоненты.
- Рабочие данные.
- Настройки.
- Секреты.
- Журналы.
- Временные файлы.
- Подготовленные обновления.

Пути определяются правилами платформы либо настройками.

Переустановка не должна автоматически уничтожать рабочие данные.

При удалении программы предоставлять явный выбор сохранения или удаления пользовательских данных.

# 6. Группы и обнаружение устройств

Каждое устройство и каждая группа получают постоянный уникальный идентификатор.

Изменение IP-адреса или названия не должно создавать новую личность устройства.

Группы обеспечивают независимость:

- Содержимого.
- Настроек.
- Административных полномочий.
- Серверной роли.
- Состояния синхронизации.

Система должна:

1. Обнаруживать доступные установки в LAN.
2. Отображать группы и их состояние.
3. Поддерживать ручное подключение.
4. Авторизовать включение новых устройств.
5. Корректно восстанавливать связь.
6. Предотвращать перезапись новых данных устаревшими копиями.
7. Контролировать перевод устройства в другую группу.

Правила обработки ранее сохранённого содержимого при смене группы утверждаются отдельно.

# 7. Роли устройств и серверов

Основные роли:

**Активный сервер:** единственный уполномоченный источник операций записи в пределах группы.

**Назначенный резервный сервер:** хранит проверенную реплику и участвует в безопасном восстановлении работы.

**Клиент отображения:** получает и показывает опубликованное содержимое.

**Административная сессия:** предоставляет управление системой в пределах прав пользователя.

Совмещение ролей допускается при совместимости и достаточных ресурсах.

## 7.1. Аварийный сервер Android

Возможность использования Android TV как аварийного сервера является желаемой функцией.

Перед реализацией необходимо:

- Создать технический прототип.
- Проверить физические устройства.
- Оценить ресурсы.
- Проверить сохранение данных.
- Проверить поддержку необходимых серверных функций.
- Определить допустимую нагрузку и ограничения.

До успешных испытаний не объявлять Android TV полноценным резервным сервером.

Предпочтительными серверными устройствами являются подходящий Windows-компьютер либо выделенный локальный сервер.

# 8. Учётные записи и права доступа

Предусмотреть две роли: **Администратор** и **Пользователь**.

Их функциональные права одинаковы, кроме управления учётными записями.

| Операция | Администратор | Пользователь |
|---|---|---|
| Просмотр информации | Да | Да |
| Создание и изменение содержимого | Да | Да |
| Предпросмотр и публикация | Да | Да |
| Удаление и восстановление записей | Да | Да |
| Доступные системные операции | Да | Да |
| Создание учётных записей | Да | Нет |
| Изменение чужих учётных записей и ролей | Да | Нет |
| Удаление учётных записей | Да | Нет |

Требования:

1. Проверять разрешения на сервере.
2. Поддерживать одновременные пользовательские сессии.
3. Предотвращать молчаливую перезапись устаревших изменений.
4. Фиксировать автора публикаций, удалений, восстановлений и изменений конфигурации.
5. Не допускать удаления или понижения последнего работоспособного администратора.
6. Защищать пароли, сессии и операции авторизации.

Возможность самостоятельной смены собственного пароля пользователем уточняется при согласовании.

Ограничивать права обычного пользователя сверх указанной модели без отдельного решения нельзя.

# 9. Содержимое и публикации

## 9.1. Типы содержимого

Обязательно поддерживать существующие данные событий, тегов и изображений, а также видео.

Для изображений и видео предусмотреть:

- Постоянные идентификаторы.
- Хранение файлов отдельно от записей базы данных.
- Контрольные суммы.
- Проверку доступности.
- Локальное воспроизведение.
- Ограничения загрузки и хранения.
- Подбор совместимых профилей для устройств.

Конкретные кодеки, разрешения, битрейты, продолжительность видео, ограничения размера файлов и требования к звуку определяются испытаниями.

Не требовать от маломощных Android TV самостоятельного перекодирования тяжёлых видео.

## 9.2. Черновики

Редактирование создаёт черновик.

Черновик не должен автоматически изменять содержимое публичных экранов.

Предусмотреть предварительный просмотр с учётом режима целевого устройства.

Интерфейс обязан отличать черновик от опубликованной версии.

## 9.3. Публикация

Публикация выполняется отдельным явным действием.

Алгоритм:

1. Проверить данные и обязательные файлы.
2. Создать согласованную опубликованную ревизию.
3. Зафиксировать целевой набор устройств.
4. Начать распространение.
5. Отследить загрузку и проверку.
6. Получить подтверждения активации клиентов.

Неполная публикация не должна подменять ранее работоспособный набор данных на экране.

## 9.4. Контроль распространения

Отображать прогресс вида:

**Обновлено 87 из 100 устройств.**

Отдельно показывать состояния:

- Ожидает.
- Получает данные.
- Загружено.
- Проверено.
- Версия активирована клиентом.
- Устройство не в сети.
- Ошибка.
- Несовместимая версия.

**Статус «Версия отображается» означает исключительно подтверждение клиентского приложения об успешной активации опубликованной версии содержимого.**

Это не доказывает, что физический телевизор включён, исправен или действительно показывает изображение пользователям.

Без дополнительных подтверждённых средств мониторинга физического оборудования такую гарантию предоставлять нельзя.

Подсчёт обновлённых устройств выполнять по подтверждениям активации, а не по факту отправки команды, получения метаданных или окончания загрузки.

При подключении или исключении устройств после начала публикации сохранять корректный учёт исходного целевого набора.

# 10. Синхронизация

## 10.1. Первоначальная передача

При присоединении клиент получает согласованный снимок необходимых данных, номер ревизии и связанные файлы.

После завершения первоначальной передачи применяются последующие изменения, начиная с соответствующей ревизии.

Запрещается:

- Использовать один файл SQLite через сетевое хранилище одновременно несколькими клиентами.
- Выполнять произвольное копирование рабочей SQLite-базы при активной записи без механизма согласованного снимка.

## 10.2. Инкрементальная передача

После первоначальной синхронизации передавать только необходимые изменения и недостающие либо изменённые файлы.

Предусмотреть:

- Постоянные идентификаторы.
- Ревизии.
- Подтверждения операций.
- Проверку целостности.
- Повторяемые безопасные операции без дублирования.
- Возобновляемые загрузки.
- Повторную полную синхронизацию при необходимости.

Не определять актуальность исключительно по системным часам устройств.

Различать ревизии полученные, загруженные, проверенные и активированные.

## 10.3. Управление нагрузкой

Ограничивать:

- Одновременные загрузки.
- Использование пропускной способности.
- Размер очередей.
- Повторные попытки.
- Объём временных файлов.

Использовать контролируемую параллельную передачу.

Приоритет отдавать интерактивным операциям и необходимым метаданным.

Передачу неизменяемых проверенных файлов непосредственно между клиентами рассматривать только как отдельную будущую оптимизацию.

## 10.4. Безопасное переключение содержимого

Новую ревизию сначала загрузить во временную область.

Затем проверить все необходимые данные и контрольные суммы.

После успешной проверки активировать её целиком.

При любой ошибке сохранять предыдущую полностью пригодную версию.

Не удалять файлы, необходимые активной публикации, сохранённым точкам восстановления или незавершённым операциям.

Ограничивать использование временного пространства, кеша и постоянного хранилища.

# 11. Автономная работа экранов

Если сервер либо сеть недоступны, полностью подготовленный клиент должен:

1. Продолжать показывать последнюю корректную опубликованную версию.
2. Сохранять доступную локальную навигацию.
3. Воспроизводить сохранённые изображения и видео.
4. Не заменять рабочее содержимое сетевой ошибкой.
5. Запускаться с локальными данными даже после перезагрузки.

Устройство, которое ещё не получило полный первоначальный набор данных, показывает понятное состояние настройки или восстановления.

**Редактирование при отсутствии безопасного авторитетного сервера приостанавливается.**

Автономное редактирование с последующим объединением конкурентных изменений не входит в первоначальную сетевую реализацию.

После восстановления безопасного авторитетного сервера редактирование возобновляется.

# 12. Сохранность данных и восстановление

## 12.1. Уровни сохранности

Использовать транзакции, устойчивые идентификаторы операций и ревизии.

Чётко различать состояния:

**«Сохраняется»** — операция ещё не зафиксирована.

**«Сохранено на основном сервере»** — операция надёжно зафиксирована на основном устройстве, но может быть потеряна при его физической утрате.

**«Защищено от потери основного сервера»** — резервный сервер подтвердил надёжную фиксацию соответствующего изменения на независимом устройстве.

**«Ожидает распространения»** — опубликованное изменение ещё не активировано всеми целевыми клиентами.

**«Версия отображается»** — клиент подтвердил активацию содержимого, без подтверждения физического состояния экрана.

Запрещено объявлять изменение защищённым от потери основного сервера, если подтверждение надёжного сохранения на резервном устройстве не получено.

При недоступном резервном сервере интерфейс обязан показывать уровень защиты фактического сохранения.

Конкретная политика подтверждения записи требует согласования. Гарантия сохранности реплицированных данных относится к утверждённому сценарию потери основного устройства, а не к одновременной утрате всех копий.

## 12.2. История операций

Фиксировать необходимые сведения:

- Идентификатор изменения.
- Ревизию.
- Автора.
- Тип операции.
- Состояние фиксации.
- Существенные сведения для диагностики и восстановления.

История должна позволять анализировать ошибочные изменения и выполнять предусмотренное восстановление.

## 12.3. Удаление и восстановление отдельных записей

Реализовать восстановимое удаление.

Восстановление отдельной удалённой записи не должно откатывать остальные актуальные изменения базы.

Сохранять связанные медиафайлы на протяжении установленного срока восстановления.

При восстановлении проверять конфликты идентификаторов и зависимостей.

Окончательное удаление выполнять только отдельной явной операцией с предупреждением о последствиях.

Сроки хранения и ограничения объёма согласовываются отдельно.

## 12.4. Резервные копии

Предусмотреть версионированные согласованные копии базы и связанных медиаматериалов.

Возможности:

- Проверка целостности.
- Несколько точек восстановления.
- Копия на отдельном устройстве.
- Экспорт на съёмный носитель.
- Проверочное восстановление во временную область.
- Безопасное применение восстановленного комплекта.

Для защиты от утраты всей площадки копию необходимо размещать за пределами площадки; локальная копия на втором компьютере этого не гарантирует.

Реплика не заменяет резервную копию, поскольку ошибочные изменения могут распространяться на неё.

## 12.5. Ошибки модулей и данных

При выявлении длительно существовавшего программного дефекта:

1. Сохранить текущую базу и историю.
2. Определить повреждённые или ошибочные записи.
3. Подготовить проверенное исправление.
4. Применить исправление с контролем результатов.

Не выполнять автоматический возврат к старой базе с уничтожением последующих корректных изменений.

# 13. Отказоустойчивость серверов

## 13.1. Первый этап резервирования

Реализовать модель:

- Компьютер A — активный сервер.
- Компьютер B — назначенный резервный сервер.

Резервный сервер должен работать в фоновом режиме без необходимости постоянно держать открытым окно отображения.

Перед испытаниями обеспечить получение полной проверенной реплики.

## 13.2. Отказ активного сервера

При отказе:

- Подготовленные клиенты продолжают автономное отображение.
- Состояние сохранения данных показывается корректно.
- Редактирование останавливается при отсутствии безопасного права записи.
- Проверяется актуальность резервной реплики.
- Передача серверной роли допускается только через безопасный протокол.

**В одной группе не должно возникать двух независимых серверов, одновременно принимающих запись.**

Потеря сетевого ответа сама по себе не является основанием для передачи прав записи.

## 13.3. Последующее автоматическое переключение

Автоматический выбор сервера — следующий этап после реализации и проверки безопасного резервирования.

Необходимо определить:

- Состав участников голосования.
- Правила большинства либо иной механизм полномочий.
- Поколения лидерства.
- Защиту от прежнего лидера.
- Проверку полноты реплики.
- Обработку разделения сети.
- Порядок возвращения прежнего сервера.

При отсутствии безопасно подтверждённого владельца права записи система продолжает локальное отображение, но не разрешает редактирование.

Два устройства без дополнительного механизма полномочий или блокировки не обеспечивают одновременно гарантированное автоматическое переключение и безопасность при разделении сети.

## 13.4. Возвращение бывшего сервера

После восстановления связи старый сервер не должен автоматически становиться активным.

Сначала он проходит проверку состояния и синхронизацию в неавторитетной роли.

Устаревшая копия не должна заменять новые данные.

# 14. Модульная система

## 14.1. Область применения

Первоначально поддерживать только модули, поставляемые разработчиком.

Каждый модуль объявляет:

- Уникальное имя и идентификатор.
- Версию.
- Поддерживаемый диапазон API ядра.
- Зависимости.
- Версию собственной схемы данных.
- Необходимые разрешения.
- Требования к ресурсам.
- Механизм проверки работоспособности.

Установка и включение требуют проверки совместимости и подлинности пакета.

## 14.2. Изоляция

Чувствительные к отказам модули запускать в отдельных контролируемых процессах.

Предусмотреть:

- Тайм-ауты.
- Ограничение запросов.
- Контроль очередей.
- Ограничение ресурсов.
- Контролируемый перезапуск.
- Защиту от бесконечных повторных запусков.
- Диагностику сбоев.

Изоляция процессов не считается полноценной защитой от исчерпания общей памяти, дискового пространства либо от вредоносного кода.

Модулям запрещается бесконтрольно изменять данные других модулей.

Способ разделения баз и схем определяется при проектировании с учётом согласованности данных.

## 14.3. Отключение и удаление

Отключение либо удаление модуля по умолчанию сохраняет его данные.

Удаление данных требует отдельной явной операции.

Необязательный отсутствующий модуль не должен препятствовать работе ядра.

Зависимости модулей должны объявляться явно.

## 14.4. Эталонный модуль

Использовать существующую функцию Events как первый модуль новой архитектуры.

Проверить:

- Принудительное завершение процесса.
- Зависание.
- Некорректный ответ.
- Недоступность хранилища.
- Перезапуск.

При этих отказах независимые компоненты должны сохранять работоспособность в установленных ресурсных пределах.

# 15. Обновления

## 15.1. Общие требования

Поддерживать проверенные локальные пакеты обновлений без обязательного Интернета.

Использовать согласованный механизм доставки, но разные политики активации для:

- Содержимого.
- Модулей.
- Ядра.
- Приложения.

Изменение содержимого обычно не требует остановки клиента.

Обновление исполняемых компонентов может требовать перезапуска.

## 15.2. Управление установкой

Предоставить варианты:

- Установить сейчас.
- Запланировать.
- Отложить.

Без перезапуска устанавливать только технически совместимые обновления.

Различать перезапуск модуля, приложения и устройства.

Время активации выбирается уполномоченным оператором с учётом допустимой политики обслуживания.

## 15.3. Защита обновлений

Пакеты должны содержать:

- Версии.
- Условия совместимости.
- Контрольные суммы.
- Криптографическую подпись.

Проверять доверенные ключи и предусмотреть их безопасную смену.

Не выполнять произвольные неподписанные файлы, обнаруженные в сети.

## 15.4. Процедура обновления

1. Получение или возобновление загрузки.
2. Проверка целостности и подлинности.
3. Проверка свободного пространства.
4. Проверка совместимости.
5. Создание согласованной точки восстановления.
6. Подготовка новой версии.
7. Проверка миграции данных во временной области.
8. Корректная остановка затрагиваемых операций.
9. Активация.
10. Проверка работоспособности.
11. Подтверждение успеха либо переход к совместимому восстановлению.

Сохранять диагностику неудачных обновлений.

Нельзя автоматически удалять последний пригодный набор данных ради освобождения диска.

## 15.5. Распространение обновлений

Сначала устанавливать обновление на пилотное устройство.

Затем выполнять контролируемое распространение с ограничением одновременных установок.

Не допускать необоснованной одновременной недоступности активного и резервного серверов.

Определить допустимый период работы разных версий.

Откат исполняемого кода разрешён только при совместимости с актуальными данными.

# 16. Совместимость версий и миграции

Главная цель — сохранение возможности переноса и использования существующего содержимого в последующих поддерживаемых версиях.

Требования:

1. Стабильные идентификаторы.
2. Версионированные форматы.
3. Преимущественно расширяющие изменения схем.
4. Документированные миграции.
5. Проверенные пути обновления.
6. Сохранение неизвестных полей там, где это безопасно.
7. Отказ от молчаливой потери информации.
8. Тестирование данных предыдущих поддерживаемых версий.

Старое приложение не обязано уметь изменять данные нового формата.

При несовместимости предоставить понятный отказ, допустимый режим чтения или совместимый экспорт, где это реализуемо.

Не обещать бесконечную поддержку любых исторических исполняемых версий.

# 17. Интерфейс отображения

Разработать и проверить отдельные адаптированные варианты для:

- Горизонтальных экранов.
- Вертикальных экранов.
- Сенсорного управления.
- Несенсорного управления.

Требования:

- Читаемая типографика.
- Достаточный контраст.
- Удобные элементы взаимодействия.
- Предсказуемая навигация.
- Соответствие расстоянию просмотра.
- Корректная адаптация изображений.
- Работа с длинными заголовками и описаниями.
- Поддержка переводов.
- Резервное отображение отсутствующих переводов.

Проверять пустые состояния, повреждённые изображения, пропавшие файлы, большие шрифты и прерванную синхронизацию.

Фоновые операции не должны надолго блокировать навигацию.

Полноэкранный режим приложения не означает полного ограничения функций ОС.

# 18. Безопасность

Обязательные требования:

1. Отказаться от фиксированных секретов разработки.
2. Исключить стандартные повторно используемые администраторские учётные данные.
3. Использовать секреты конкретной установки.
4. Защищать сессии.
5. Проверять все права на сервере.
6. Ограничивать попытки входа.
7. Проверять принадлежность устройств группам.
8. Защищать операции изменения данных.
9. Ограничивать размеры файлов и запросов.
10. Проверять обновления.
11. Определить защиту учётных данных и целостности содержимого при передаче по LAN.

Локальная сеть не должна считаться заведомо доверенной.

# 19. Диагностика и обслуживание

Предусмотреть режимы:

**Обычный:** вся доступная функциональность.

**Безопасный:** проблемные модули отключаются, ядро и сохранённое отображение остаются доступными, насколько это позволяет состояние устройства.

**Восстановление:** диагностика целостности, экспорт, проверка копий, подготовка восстановления.

Собирать ограниченные по объёму журналы:

- Запуска и остановки.
- Ошибок ядра.
- Сбоев модулей.
- Синхронизации и задержек.
- Последних подтверждённых ревизий.
- Обновлений.
- Использования диска и ресурсов.
- Восстановления.

Обеспечить понятные сообщения о неисправностях.

Диагностический архив должен удалять секреты из экспортируемых сведений.

Предусмотреть локальный способ обслуживания без работоспособной страницы администрирования и сетевого обнаружения.

# 21. Испытания

## 21.1. Функциональные проверки

Проверить:

- Первоначальную установку.
- Запуск и перезапуск.
- Обнаружение групп.
- Авторизованное присоединение.
- Права доступа.
- Редактирование.
- Черновики.
- Предварительный просмотр.
- Публикацию.
- Синхронизацию.
- Автономное отображение.
- Удаление и восстановление отдельных записей.
- Обновление и восстановление.
- Работу и отказ модулей.

## 21.2. Два отдельных компьютера

Испытания A/B:

1. Изменить данные на A, проверить реплику B и активацию клиентами.
2. Корректно остановить A, проверить автономную работу клиентов и управляемую передачу роли.
3. Аварийно остановить A, проверить отсутствие частичных публикаций и потерянных подтверждённых реплицированных изменений.
4. Разделить сеть между A и B, проверить отсутствие двух независимых серверов записи.
5. После разрешённой передачи роли B вернуть A, проверить невозможность перезаписать новые данные старой копией.
6. Остановить B при работающем A, проверить корректную индикацию локального сохранения без резервной защиты.
7. Перезапустить клиентов без доступа к A, проверить автономный запуск.
8. Прервать передачу видео и обновление, проверить восстановление прежней рабочей версии.

Для потенциально разрушительных испытаний использовать только изолированные тестовые данные.

## 21.3. Дополнительные отказы

# 23. Критерии приёмки

Для принятия соответствующего этапа или всей системы необходимо подтвердить применимые требования.

Общие критерии:

1. Исходные функции MVP сохранены.
2. Поддерживаемые старые данные открываются или корректно мигрируют.
3. Система работает в LAN без Интернета.
4. Подготовленные клиенты продолжают автономный показ после отказа сервера и перезапуска.
5. Черновики не появляются на публичных экранах без публикации.
6. Новое содержимое активируется только после полной проверки.
7. Прогресс публикации основан на подтверждениях активации клиентов.
8. Интерфейс не утверждает, что физический экран работает, только на основании клиентского подтверждения.
9. Удалённые записи можно восстанавливать отдельно, вместе с сохранёнными связанными материалами.
10. Группа не допускает двух независимых серверов записи.
11. Данные, отмеченные как защищённые от потери основного сервера, действительно подтверждены резервным устройством.
12. Отказ отдельного модуля не вызывает необоснованный отказ независимых компонентов.
13. Неудачное обновление оставляет совместимый путь восстановления и сохранённые данные.
14. Проверены установочные пакеты на чистых устройствах.
15. Поддержка конкретных платформ подтверждена физическими испытаниями.
16. Утверждённые показатели нагрузки и производительности подтверждены измерениями.
17. Документация соответствует реализованной версии.

# 27. Итоговый результат

Kiosk v2.0 должен стать единым, простым в эксплуатации и модульным программным продуктом для управления группами информационных экранов в локальной сети.

Обязательные свойства итоговой системы:

**Автономность:** работа без обязательного подключения к Интернету.

**Непрерывность отображения:** подготовленные клиенты продолжают использовать локальные опубликованные данные при отказе сервера.

**Согласованность:** изменения не приводят к конфликтующим активным серверам или частичным публикациям.

**Сохранность:** уровни фиксации данных показываются достоверно, а резервные копии и восстановление проверяются практически.

**Модульность:** отказ необязательного модуля не должен необоснованно нарушать работу остальных компонентов.

**Совместимость:** обновления и миграции выполняются контролируемо, без молчаливой потери поддерживаемых данных.

**Наблюдаемость:** система сообщает о фактическом состоянии синхронизации и активации, не приписывая себе непроверенных возможностей физического мониторинга экранов.

**Проверяемость:** все технические гарантии подтверждаются соответствующими испытаниями.

**Статус документа:** единая согласованная по формулировкам редакция технического задания. Неутверждённые вопросы раздела 24 и предварительные количественные показатели должны быть согласованы до принятия соответствующих обязательств в разработку.
