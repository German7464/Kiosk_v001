# Architecture

## Module boundaries

The source application uses Flask, SQLite, Jinja, HTML/CSS/JavaScript and Pillow. `run.py` starts development Flask. `serve.py` starts Waitress. Windows packaged startup uses the Launcher and a separate SCM service. Android source is in this checkout. Use the [specification](TZ_RECONCILED.md) for target architecture and the [ledger](TZ_PROGRESS.md#current-checkpoint) for evidence.

| Boundary | Source and interface |
| --- | --- |
| Application setup, shared helpers and content | `kiosk/app.py`, `config.py`, `database.py`, `core/`, `templates/`, `static/`, `translations/` |
| Human-facing editing and public data | [Admin](../kiosk/features/admin/README.md), [public API](../kiosk/features/api/README.md) |
| Windows install, service and desktop | [Launcher](../kiosk/launcher/README.md#purpose) |
| Protected HTTP edge | [Transport](../kiosk/transport/README.md#purpose). Caddy fronts loopback Waitress in managed HTTPS. |
| Event artifacts and local rendering | [Publication](../kiosk/publication/README.md#contract), [Windows display](../kiosk/display/README.md#startup-readiness-and-recovery), [Android](../android/README.md#code-map) |
| Enrollment, assignments, byte transfer and receipts | [Delivery](../kiosk/delivery/README.md) and the [wire contracts](../contracts/README.md) |
| Authority and human maintenance | [Trust](../kiosk/trust/README.md), [Maintenance](../kiosk/maintenance/README.md#security-boundary), authenticated Content service API |

Keep route, database, business and rendering logic in their respective layers. Share the display logic across Kiosk, TV and preview. Source/MVP runtime data lives under `instance/`; use the Launcher for installed storage. Module organization alone establishes no process-level isolation. Keep local evidence outside Git.

## Supplemental owner decisions

These bounded decisions supplement the approved revision. Their dated originals are indexed under [Acceptance and owner decisions](archive/README.md#acceptance-and-owner-decisions). See [trust recovery](../kiosk/trust/README.md#recovery-single-administrator-password-protected-backup) for the implementation contract.

- Routine LAN certificate and access renewal runs automatically without Internet or manual key selection. Maintain a single-administrator workflow with a separately password-protected recovery backup. Use explicit re-pairing if recovery material is unusable. Preserve accepted offline content after expiry and require administrator-confirmed recovery if safe admission cannot resume. Separate test installation first; retained installations and keys need separate migration authority.
- The initial administrator-assisted maintenance interval is 90 days. Individual leaf and access lifetimes are independent. Align issuer and delegation horizons, warnings and overlap. A nominal 90-day expiry alone does not demonstrate 90 days of unattended operation. The annual proposal and 600-day future-issuer inventory remain unselected.
- Use one generic Android APK and a guided one-time public CA install through supported Android Settings. Authenticate the CA independently, verify WebView HTTPS before login and preserve strict trust and origin checks. Routine renewal remains automatic. The earlier blanket prohibition on an initial manual CA install is superseded.
- Human maintenance uses login/password; make sessions bounded and cancellable, isolate lock/user switching, use scoped role bundles and bind a single-use QR/manual-code request. New privilege requires valid authority or recovery. Retain drafts and valid past publications after logout, blocking or revocation. New publication and changed targets require current approval. Keep committed work distinct from saved drafts and pending approvals. Use the [Maintenance service](../kiosk/maintenance/README.md#human-model) for implemented behavior and [security boundary](../kiosk/maintenance/README.md#security-boundary) for placement limits. A browser approval must use the trusted Maintenance boundary; Content-origin signing does not provide that assurance.

## Selected roaming-user publishing workflow - owner decision 2026-11-16

This section supersedes the earlier proposed fixed-PC/two-signature/per-organization-APK alternatives. The selected QR editing and trusted-app publication workflow includes the minimum Events draft dependency. Stage gates and measured acceptance are in [the ledger](TZ_PROGRESS.md). Preserve current TZ roles and accepted delivery/updater contracts unless a versioned opt-in extension is required.

1. **Identity and scope.** Separate user account, user-device publisher identity, display enrollment and browser session. Administrator and User both edit/publish content per TZ8; only Administrator manages other accounts/infrastructure. A display credential or successful browser login never grants publisher/admin signing power. Server may also display as kiosk, but must not hold publisher-authorizing/private user signing keys if resistance to full server compromise is claimed. Private admin trust authority remains outside that server OS.
2. **Provisioning.** One generic Android APK; owner approved guided one-time OS/user CA setup. Prepare only public CA, authenticate installation independently, guide supported Settings and verify actual native/WebView TLS before credentials. No silent trust install/bypass, no arbitrary external origin. Local keys use platform custody and are not derived from password or copied between devices. Existing accepted original phone app remains protected.
3. **First and later devices.** Administrator initializes first user/device authority through a trusted local action; server password/DB account creation alone cannot create display-verifiable publisher authority. Each additional user-device generates its own key and proves possession. An already authorized app may explicitly authorize that same user's new device within its signed delegation; it cannot change user/role/group/scope or grow permissions. Cross-user/first-device registration and recovery require Administrator. Signed bounded device permissions chain to a pinned independent authority; server transports records but cannot replace/replay them as policy. No unbounded delegation depth. No device/OS fingerprint as cryptographic identity.
4. **Browser QR login.** A short-lived random single-use challenge is bound to the requesting browser's secret session and exact trusted origin. Scanning only opens a review; explicit acceptance by an unlocked authorized app establishes that browser session with the user's existing role, rotating its session identifier. QR is a login challenge, not a credential/secret/signing key/bootstrap or automatic enrollment. Distinguish Login, Add my device and Publish challenges by domain/type. Check origin/browser summary and matching confirmation code; never auto-accept an unsolicited QR. Limit pending requests/polling/attempts; exclude tokens/codes/cookies from logs. No universal PIN or SMS/cloud dependency.
5. **Sessions and passwords.** Password login remains a supported fallback for permitted server operations; it cannot mint publisher keys or bypass trusted-app publication. Browser sessions on shared machines are temporary, listed and remotely revocable; logout invalidates server sessions, not just local cookies. App lock/expiry/shared-device logout prevents use by the next user; loss of all trusted apps uses a bounded admin recovery workflow. Owner can move between own Windows/Android devices without an admin action on every publication. All new account/device authority and revocation remain separately protected; compromising the server's password verifier is not publisher authorization.
6. **Drafts.** Server-side versioned Events drafts are separate from active/public routes and packages. Login permits editing with role checks and CSRF; saving never changes display. Ready dependencies, immutable publication plan, conflict checks and authorship follow TZ9.2/9.3. Migrate only disposable Events fixtures in this task. Published dependency snapshots cannot change during approval; concurrent changes require a new review. Do not label current immediate-public MVP editing as draft support.
7. **Explicit publication.** The user reviews exact locally validated immutable content in their own app and presses Publish once (from any authorized own Windows/Android device). Browser edits may be approved from phone. One user-device signature is sufficient, no two keys derived from login/password and no admin countersignature for every publication. Native review/signing must be isolated from server-controlled WebView: no blind JS signing bridge, arbitrary file/hash signing, auto-approval, remote UI substitution or unsigned remote renderer/script execution. Use existing validated renderer/package pipeline and bounded inventory; no hand-entered crypto parameters.
8. **What is signed.** A versioned/domain-separated approval binds group, user/device authorization, immutable publication identity and complete file hashes, dependency/renderer build identities, intended target/profile/mode configuration and replay/conflict constraints. Server assignment counters alone must not authorize arbitrary old signed content/new targets. Retain explicit legitimate rollback/reassignment as a newly approved operation. Clients verify trusted signer authorization plus exact package/target/context before activation and retain prior accepted content on error. Cross-publisher concurrent plans and a newly initialized display receiving withheld older valid data need an explicit honest freshness policy; do not claim a local counter solves omniscient freshness or whole-disk rollback. No silent unsigned downgrade in the isolated signed mode.
9. **Distribution and recovery.** Server distributes already approved content and signed permission/revocation records; receiving displays verify, not co-sign. Plain DB copy/hash list is not trust. Permissions use actual public keys, identifiers, bounded scope, monotonic policy versions and expiration; protect trust-anchor/key additions, role changes and app updates from delivery-server bypass. Revocation/expiry blocks new admission, not retained offline content. Offline devices cannot instantly learn revocation; use last authenticated bounded policy and explicit recovery after expiry, not silent widening. Server compromise can still block updates; compromised publisher app/OS or malicious authorized publisher remains a limit. Same-OS server signing cannot support a full server-compromise-resistance claim.
10. **Maintenance.**90-day administrator-assisted maintenance remains selected; routine TLS/access renewal automatic LAN. Choose practical protocol limits/margins in module contract and test them without asking the owner to invent crypto constants. Align device policy and trust/issuer/delegation horizons with warnings and overlap. No future600-day key inventory,10-year promise, retained migration or mandatory recurring manual root use for normal publication.

Reuse: [Telegram short-lived explicitly accepted QR login](https://core.telegram.org/api/qr-login) for UX; existing Kiosk pairing/Nayuki/local renderer/session revocation for implementation; [Mender signing separation](https://docs.mender.io/artifact-creation/sign-and-verify) and [TUF delegated metadata](https://theupdateframework.io/docs/metadata/) for trust design. Use supported platform crypto/keystores, existing maintained cryptographic primitives and canonical formats; no Telegram/RustDesk source copy or complete new identity/remote-control platform. Similar UX is not protocol compliance or proof of security.

Acceptance criteria for the selected workflow include both roles; QR accept, reject, expiry, replay, session swap and logout; same-user admission and escalation refusal; browser save without public changes; exact-plan native approval from Windows and Android; forged, modified, replayed or unauthorized-target content and forged policy rejected despite content-server control; actual ready and persistent offline restart on the affected native displays; and ordinary recovery without data loss. See the [ledger](TZ_PROGRESS.md#dated-evidence) for the accepted scope.


### Selected deployable separation - owner decision 2026-11-17

Owner explicitly selects separate processes on ONE OS for initial implementation, with an installation/setup choice and a supported later move to separate OS instances (VMs or physical computers) WITHOUT recreating the product installation/data. This supersedes the recommendation to require VMs initially and the earlier outside-content-OS custody requirement only for the selected cohosted runtime identity/permission/portal services. User publication private keys remain at their authorizing endpoints; no automatic relocation of publisher keys or offline root/recovery authority into the content server. IdP product and exact grant/receipt formats remain unselected.

Required implementation boundaries:
- Two functional sides: content service (draft/media/package storage and delivery) and trusted maintenance/identity/permission/acceptance side. They may each contain several processes. Same versioned authenticated HTTPS API contract in local and separated placement; never make security depend on localhost, a shared live database, shared private-key directory or direct access to the other service's files.
- Cohosted services use distinct least-privileged service identities, separately protected data/config/secrets and separate web origins/cookie scopes. Content service cannot edit trusted portal assets, read its runtime issuer keys, mint user/device grants or use an unrestricted signing endpoint. No SYSTEM/shared administrator account for both sides as a shortcut. An origin change does not by itself isolate OS compromise.
- Installation/setup presents Combined (both sides on this OS) or Separated (install/connect the required side with explicit trusted counterpart pairing). It must not require users to distinguish a VM from a physical machine: service role, authenticated endpoint and identity are the relevant software configuration. Explain the actual protection level plainly; do not label Combined as resistant to full host-OS takeover. Separated VMs still share host/hardware risks.
- Keep externally used service identities/addresses configurable and authenticated. Plan stable LAN names/trust continuity so relocation does not force recreation of accounts, device enrollment, group IDs or publication history. Address changes are not authority replacement; no automatic trust acceptance, wildcard origins/CORS, widened browser cookie domain or TLS bypass to make relocation easier.
- Add an administrator-only Relocate service workflow in existing setup/maintenance: preflight destination/version/trust/storage, verified consistent encrypted transfer of the moved side's state, explicit exclusive cutover, endpoint/trust update and health/continuity checks. Stop/fence old active issuance/writes before enabling the destination; never leave two independent active copies or blindly restore an old snapshot after new writes. Bounded maintenance interruption is acceptable; no promise of live migration/replication or automatic hypervisor provisioning.
- Preserve user accounts/password verifiers, staff memberships/scoped grants, group/display identities/profiles, drafts/media, committed publications/acceptance evidence, policy/ancestry floors and history. Rotate/rebind runtime credentials explicitly as needed. DPAPI/Keystore objects are not assumed portable; protected exportable authority material or authorized replacement/overlap must be designed and tested, not raw profile copying. Human sessions may require renewed login; neither silent credential resurrection nor compulsory device re-pairing is an acceptable migration shortcut.
- Acceptance for the coherent implementation must exercise real Combined setup, then move one side to another OS on disposable data using the same supported workflow, demonstrating preserved records/identities, existing display continuity, new publication, rejection of the old active service and safe interruption recovery. Reuse accepted unchanged campaigns. Future arbitrary hypervisors/hosts are not certified by one migration test; retained installations remain protected.

Security boundary expressly changes with placement: Combined limits an application/service compromise through OS permissions but cannot protect runtime authorities/portal against full administrator/kernel compromise of that OS. Separated placement can protect against takeover of the content guest OS when trust service and management credentials are outside its control; hypervisor/host takeover and publisher endpoint compromise remain limits. Document placement in diagnostics and acceptance, not as equivalent security. Initial implementation selection is not completed implementation, production deployment, automatic retained migration, Git-write permission, full stage7 backup or stage8 failover authorization. See the [current checkpoint](TZ_PROGRESS.md#current-checkpoint).

### Adoption gate

For each selected feature, executor reports reuse/extend/build comparison, exact upstream version/commit and license/notices, dependency/security maintenance, adapter boundaries and affected checks. Pin/package assets locally for offline operation; keep application data contracts independent of editor internals. Prototype GridStack first when stage6 is actually selected: stable block/data IDs, save/reload across four display profiles, mouse/touch, conflict rejection and continued old-client display. No mandatory dependency follows from this shortlist; stage7–10 remain unauthorized. No project distribution license was found in the inspected PC1 tracked files, so do not assume copyleft integration compatibility.
