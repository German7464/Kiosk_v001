# Architecture

## Approach

Kiosk_v001 provides a modular Flask web application backed by SQLite. Public display routes and the admin/API blueprints share content storage, image processing, translations and content-version helpers. Feature packages are part of this application, not isolated module processes.

Source/MVP startup uses `run.py` for Flask development or `serve.py` for Waitress. The stage 3 Windows package adds a separate SCM service and a Tk/ttk Launcher. Managed HTTPS supervises Caddy in front of loopback Waitress. See the [Launcher](../kiosk/launcher/README.md) and [transport](../kiosk/transport/README.md) documentation for deployment details.

The distributed architecture in [the approved specification](TZ_RECONCILED.md) remains the target. Existing Events package preparation/store and the shared local renderer are implemented in `publication/`; the bounded Windows WebView2 shell/coordinator is in `display/`. Opt-in `delivery/` adds isolated enrollment, assignment/artifact transport, ready receipts and the operator publication UI. Its presence does not enable delivery in default installed startup. Android implementation lives in PC2's separate checkout; PC1's Android README is a branch/recovery pointer, not the implementation inventory.

Persistent offline Events and bounded server/Android delivery have evidence in [the sole ledger](TZ_PROGRESS.md), with exact platform/build limitations. Full discovery, device/profile administration and trust lifecycle remain incomplete. Page/draft authoring and Events module extraction belong to stage 6; replication, signed updates and complete independent recovery remain later-stage targets. Package organization is not evidence of process isolation or release readiness.

## Separation Rules

- `app.py`, `config.py` and `server.py` provide application setup, configuration and source server startup.
- `core` contains shared credentials, session/request security, images, translations and content helpers.
- `features` contains the admin and public API blueprints. Each major feature module has one `README.md`.
- `launcher` contains installed storage, Windows installation/service control, runtime supervision and the desktop interface.
- `transport` contains managed HTTPS configuration, runtime and Windows helpers.
- `publication` contains Events export/verification, local persistent package storage and the shared client-owned renderer.
- `display` contains Windows native hosting, local view/cache coordination and runtime resource guards.
- `delivery` contains opt-in server-side device authorization, revision transport, receipt persistence and operator accounting; its SQLite database is separate from working Events storage.
- `templates` contains HTML templates only.
- `static` contains CSS, JavaScript, uploaded public assets, and interface assets.
- `database.py` contains database connection and initialization helpers.
- `instance` contains source/MVP runtime data, including the SQLite database, session key and original uploads. Installed machine data is separated under ProgramData as described in the Launcher documentation.
- `logs` contains ignored local development evidence and test reports; installed service logs use their separate machine-data directory.
- `translations` contains interface translation files.
- Business logic must not be placed inside templates.
- Database logic must not be mixed with routes.
- Kiosk, TV, preview, and admin modes should reuse shared logic where possible.

First phone server trust precedes password login; no warning bypass/root auto-install.

## Private LAN PKI and Android WebView - research 2026-11-16

Research only, no design/custody/deployment approval. Standard two-tier PKI: offline root, online issuer, automatic leaf renewal, planned issuer/root maintenance. [Smallstep production](https://smallstep.com/docs/step-ca/certificate-authority-server-production/) requires root access for intermediate rotation; [renewal](https://smallstep.com/docs/step-ca/renewal/) automates leaves. [AD CS](https://learn.microsoft.com/en-us/windows-server/identity/ad-cs/certification-authority-role) separates these roles. No evidence found that600 days of future issuer private keys is necessary. Prefer justified issuer lifetime and explicit exceptional maintenance over an unproved multi-issuer scheduler. TLS renewal does not renew Kiosk group authority or grant admin/publication rights.

[Caddy local HTTPS](https://caddyserver.com/docs/automatic-https#local-https) automates local leaves/intermediates but keeps its root key available: adopting that default changes approved offline-root custody. [step-ca](https://github.com/smallstep/certificates), maintained Apache-2.0, is self-hosted; integration cost includes another supervised process, protected keys, policy/configuration and backup. It does not solve Android first trust, Kiosk authority or fencing; no replacement without demonstrated benefit.

[Android NSC](https://developer.android.com/privacy-and-security/security-config) supports bundled roots and opt-in user roots, not a documented arbitrary runtime-root setter for WebView. [DevicePolicyManager](https://developer.android.com/reference/android/app/admin/DevicePolicyManager) permits CA installation by authorized device/profile owners or delegated installers, not ordinary apps; modern apps must opt into user roots. Managed enrollment permits one APK but adds deployment work and changes approved app-only trust, requiring owner approval. Per-install signed APK embedding public CA is plausible, not established as a common product pattern; offline build/signing custody and compatible root updates add cost. Native custom trust does not configure WebView TLS.

Comparable products: [Fully Kiosk](https://www.fully-kiosk.com/docs/en/faq/ssl) documents device certificate installation and selected bundled public roots; [Ignore SSL Errors](https://www.fully-kiosk.com/docs/en/configuration/advanced-web) explicitly warns of unsafe TLS and must not be copied. [Home Assistant Companion](https://companion.home-assistant.io/docs/troubleshooting/faqs/) documents Android self-signed certificate handling. Client-authentication certificates are separate from server CA trust. References are not adopted libraries or hardware acceptance; no implementation/test performed in this research.

Check origin/browser summary and matching confirmation code; never auto-accept an unsolicited QR. Limit pending requests/polling/attempts; exclude tokens/codes/cookies from logs. No universal PIN or SMS/cloud dependency.
5. **Sessions and passwords.** Password login remains a supported fallback for permitted server operations; it cannot mint publisher keys or bypass trusted-app publication. App lock/expiry/shared-device logout prevents use by the next user; loss of all trusted apps uses a bounded admin recovery workflow. Owner can move between own Windows/Android devices without an admin action on every publication. All new account/device authority and revocation remain separately protected; compromising the server's password verifier is not publisher authorization.

Use existing validated renderer/package pipeline and bounded inventory; no hand-entered crypto parameters.

Clients verify trusted signer authorization plus exact package/target/context before activation and retain prior accepted content on error. Cross-publisher concurrent plans and a newly initialized display receiving withheld older valid data need an explicit honest freshness policy; do not claim a local counter solves omniscient freshness or whole-disk rollback. No silent unsigned downgrade in the isolated signed mode.

Permissions use actual public keys, identifiers, bounded scope, monotonic policy versions and expiration; protect trust-anchor/key additions, role changes and app updates from delivery-server bypass. Offline devices cannot instantly learn revocation; use last authenticated bounded policy and explicit recovery after expiry, not silent widening. Server compromise can still block updates; compromised publisher app/OS or malicious authorized publisher remains a limit. Same-OS server signing cannot support a full server-compromise-resistance claim.

No future600-day key inventory,10-year promise, retained migration or mandatory recurring manual root use for normal publication.

Recommended minimal model for review:
- One visible first-login flow may establish the user's session and their device permission together; internal session, installation, user-device signing grant and display identity remain distinct. QR/code approval is explicit, short-lived, single-use, origin/key/user-bound and attempt-limited. An arbitrary browser session must not gain device-enrollment power.

- Shared terminals belong to the organization/group, not the last employee. Switch users without moving the terminal's group/profile or sharing admin/publisher keys. Keep one active operator per app, isolated user material and continuing independent display operation.

Administrator-only Decommission removes the organization's display enrollment; an employee's personal logout/revocation must not silently decommission a kiosk.
- My devices lists active sessions and retained authorized devices separately, with last contact rather than invented online status. Revocation at an online server can end sessions promptly; disconnected clients learn signed revocation later. Accepted public offline content remains subject to the existing retention policy.
- Proposed permission assignment is user/team + named permission bundle + resource scope. Keep device groups/trust domains distinct from staff teams. Start with no nesting, deny ungranted operations, and no automatic rights from a device's previous user. Users may belong to several teams; a display still belongs to one device group. Cross-independent-group identities remain outside the current demonstrated contract.

This changes TZ8's current two-role/equal-content-rights rule and needs explicit owner approval. No silent new global multi-group authority or unrestricted redelegation.

A compromised delivery server could impersonate the user. Lowest-change recommendation: first publication-device use by each user requires their own trusted app/admin approval once; subsequent sign-ins on that retained user-device grant need no repeated approval. Exact password-only first-use publishing requires separately designed independent LAN identity/permission issuance (possibly a separately hosted upstream identity service), or an explicitly reduced server-compromise boundary. No ready-made product alone proves that integration secure. Local reauthentication/key isolation on shared OS accounts also needs implementation evidence.

Owner explicitly selects separate processes on ONE OS for initial implementation, with an installation/setup choice and a supported later move to separate OS instances (VMs or physical computers) WITHOUT recreating the product installation/data. This supersedes the recommendation to require VMs initially and the earlier outside-content-OS custody requirement only for the selected cohosted runtime identity/permission/portal services. Required implementation boundaries:
- Two functional sides: content service (draft/media/package storage and delivery) and trusted maintenance/identity/permission/acceptance side. They may each contain several processes. Same versioned authenticated HTTPS API contract in local and separated placement; never make security depend on localhost, a shared live database, shared private-key directory or direct access to the other service's files.
- Cohosted services use distinct least-privileged service identities, separately protected data/config/secrets and separate web origins/cookie scopes. Content service cannot edit trusted portal assets, read its runtime issuer keys, mint user/device grants or use an unrestricted signing endpoint. No SYSTEM/shared administrator account for both sides as a shortcut. An origin change does not by itself isolate OS compromise.
- Installation/setup presents Combined (both sides on this OS) or Separated (install/connect the required side with explicit trusted counterpart pairing). It must not require users to distinguish a VM from a physical machine: service role, authenticated endpoint and identity are the relevant software configuration. Explain the actual protection level plainly; do not label Combined as resistant to full host-OS takeover. Separated VMs still share host/hardware risks.
- Keep externally used service identities/addresses configurable and authenticated. Plan stable LAN names/trust continuity so relocation does not force recreation of accounts, device enrollment, group IDs or publication history. Address changes are not authority replacement; no automatic trust acceptance, wildcard origins/CORS, widened browser cookie domain or TLS bypass to make relocation easier.
- Add an administrator-only Relocate service workflow in existing setup/maintenance: preflight destination/version/trust/storage, verified consistent encrypted transfer of the moved side's state, explicit exclusive cutover, endpoint/trust update and health/continuity checks. Stop/fence old active issuance/writes before enabling the destination; never leave two independent active copies or blindly restore an old snapshot after new writes. Bounded maintenance interruption is acceptable; no promise of live migration/replication or automatic hypervisor provisioning.
- Preserve user accounts/password verifiers, staff memberships/scoped grants, group/display identities/profiles, drafts/media, committed publications/acceptance evidence, policy/ancestry floors and history. Rotate/rebind runtime credentials explicitly as needed. DPAPI/Keystore objects are not assumed portable; protected exportable authority material or authorized replacement/overlap must be designed and tested, not raw profile copying. Human sessions may require renewed login; neither silent credential resurrection nor compulsory device re-pairing is an acceptable migration shortcut.
- Acceptance for the coherent implementation must exercise real Combined setup, then move one side to another OS on disposable data using the same supported workflow, demonstrating preserved records/identities, existing display continuity, new publication, rejection of the old active service and safe interruption recovery. Reuse accepted unchanged campaigns. Future arbitrary hypervisors/hosts are not certified by one migration test; retained installations remain protected.
