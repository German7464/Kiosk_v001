# Тест-кейсы

## Назначение приложения

В приложении приведены ручные и автоматизированные тест-кейсы, применяемые для проверки программного продукта Kiosk_v001. Ручные тест-кейсы описывают пользовательские сценарии администратора, посетителя киоска, зрителя TV-экрана и локального оператора. Автоматизированные регрессионные проверки фиксируют ключевое текущее поведение системы и выполняются средствами `unittest` с использованием временной SQLite-базы данных и временных каталогов загрузок.

В поле «Result» значение `Passed` указано для сценариев, которые уже покрыты автоматизированными регрессионными проверками или ранее выполнявшимися проектными проверками. Значение «Не заполнено» оставлено для визуальных, сетевых и EXE-проверок, которые должны быть окончательно подтверждены вручную при финальном оформлении курсовой работы.

## Таблица В.2 — Автоматизированные регрессионные проверки

Автоматизированные проверки расположены в файле `tests/test_mvp_smoke.py`. Они не заменяют визуальную приемку, но защищают основные маршруты, работу данных и критичные регрессионные сценарии перед сборкой и последующими изменениями.

| Область проверки | Что проверяется | Особенности выполнения |
| --- | --- | --- |
| Доступность маршрутов | `/kiosk`, `/kiosk/events`, `/tv`, `/preview`, `/admin/login`, `/api/version`, `/api/events`, `/api/tags` возвращают ожидаемые HTTP-статусы. | Используется Flask test client без запуска браузера. |
| Административная авторизация | Успешный вход, отказ при неверном пароле, выход из системы, защищенность `/admin` до входа. | Проверка выполняется на временной базе данных. |
| Ссылка на предпросмотр | `/admin` содержит ссылку на `/preview`, не показывает raw translation key и не выводит вопросительные знаки вместо текста. | Дополнительно проверяется русская локализация ссылки. |
| Видимость событий в API | Скрытые события не попадают в `/api/events`, активные события отображаются, `/api/events/<id>` возвращает активное событие. | События создаются внутри временной базы теста. |
| Теги | Создание, редактирование, назначение тега событию и удаление тега отражаются в API-данных события. | Проверяется связь `event_tags`. |
| Настройки и `content_version` | Сохранение настроек увеличивает версию содержимого, сохраняет `site_title`, `interface_language`, тексты стартовой страницы киоска. | Проверяются языки `ru`, `en`, `de`. |
| Изображения и системная иконка | Загрузка изображения события создает `original`, `kiosk`, `tv`, `thumb`; исходник не отдается публично; загрузка иконки сохраняет публичный оптимизированный файл. | Используются временные каталоги загрузок. |
| Protected fullscreen unlock | `/admin/fullscreen/validate` возвращает только `success`; неверные данные дают `false`, текущие верные данные дают `true`; после смены пароля старый пароль не подходит. | Пароли не сравниваются на клиенте и не возвращаются в ответе. |
| Kiosk inactivity warning | `/kiosk/events` содержит разметку предупреждения, старые raw translation keys не выводятся; JS содержит задержку 120 секунд, countdown 30 секунд, сброс активности и переход на `/kiosk`. | Проверяется код и HTML-разметка без браузера. |
| Startup helpers | `serve.py` по умолчанию использует `0.0.0.0`, `--host 127.0.0.1` остается доступным, `--no-client` отключает автозапуск клиента/браузера, ClientKiosk fallback тестируется через mocks. | Внешние программы и браузер не запускаются. |
| Runtime `SECRET_KEY` | Секрет Flask создается во временном runtime-каталоге, не равен `dev`, переиспользуется при повторном старте и может быть переопределен переменной окружения. | Реальный `instance/secret_key.txt` не затрагивается. |
| CLI-сброс пароля | Сброс пароля работает на временной базе, сохраняется хэш пароля, временный пароль выводится только командой сброса. | Реальный `instance/kiosk.sqlite` не используется. |

## Вывод по тестированию

Подготовленные ручные тест-кейсы охватывают основные пользовательские сценарии Kiosk_v001: вход администратора, управление событиями и тегами, загрузку изображений, настройку системы, работу публичных экранов, LAN-запуск, EXE-запуск и сброс пароля. Автоматизированные регрессионные проверки дополняют ручное тестирование и позволяют быстро убедиться, что ключевые маршруты, API, обработка данных, механизм обновления, fullscreen unlock, startup helpers, runtime-секрет и обработка изображений продолжают работать после изменений.

Совместное использование ручных и автоматизированных проверок подтверждает работоспособность основной функциональности системы. Визуальные, сетевые и EXE-сценарии требуют финальной ручной отметки результата после подготовки итоговых скриншотов и проверки собранного приложения.
