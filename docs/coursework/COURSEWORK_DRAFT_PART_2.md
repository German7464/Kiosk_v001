# Черновик курсовой работы. Глава 2

## 2 Теоретическая часть

Данная глава содержит теоретическую основу проектирования локальной клиент-серверной информационной системы для отображения событий на публичных экранах. Рассматриваются принципы клиент-серверного взаимодействия, особенности информационных киосков и Smart TV, требования к интерфейсам публичных экранов, а также средства моделирования, которые могут быть использованы для описания системы Kiosk_v001 в курсовой работе.

Теоретическая часть не заменяет описание реализации. Ее назначение состоит в том, чтобы обосновать выбранный подход и показать, какие общие принципы проектирования применимы к разработке локальной системы управления карточками событий. Конкретная структура программы, модули, маршруты, база данных и тестирование будут подробнее рассмотрены в практической главе.

## 2.1 Локальные клиент-серверные информационные системы

Клиент-серверная информационная система представляет собой способ организации программного решения, при котором функции хранения, обработки и предоставления данных сосредоточены на сервере, а пользователи взаимодействуют с системой через клиентские приложения. В веб-системах роль клиента чаще всего выполняет браузер. Он отправляет HTTP-запросы, получает HTML-страницы, статические файлы или JSON-данные и отображает результат пользователю.

Серверная часть отвечает за прием запросов, выполнение бизнес-логики, работу с базой данных, проверку прав доступа, формирование ответов и обслуживание статических ресурсов. В информационной системе событий сервер хранит карточки мероприятий, теги, настройки, изображения и служебные данные. Он также определяет, какие события должны быть показаны публичным экранам, а какие остаются скрытыми в административной панели.

Клиентская часть выполняет другую задачу. Она отображает интерфейс, реагирует на действия пользователя, отправляет запросы к серверу и обновляет видимую информацию. Для публичных экранов клиент может быть интерактивным, как экран киоска, или пассивным, как TV-режим. В обоих случаях клиент получает данные от сервера, но способ представления информации зависит от сценария использования.

В веб-приложениях обмен между клиентом и сервером организуется через маршруты и API endpoints. Маршрут может возвращать готовую HTML-страницу, например страницу административной панели или экран киоска. API endpoint обычно возвращает структурированные данные, например JSON со списком событий или текущей версией контента. Такое разделение удобно: серверные шаблоны формируют основные страницы, а JavaScript на клиенте может периодически получать обновленные данные без полной перестройки архитектуры.

Локальное LAN-развертывание подходит небольшим учреждениям, учебным организациям, офисам и площадкам мероприятий, где экраны находятся в одной сети, а обязательная публикация системы в интернете не требуется. В такой схеме один компьютер может выполнять роль сервера, а киоск, Smart TV, рабочее место администратора или телефон для проверки открывают нужные страницы по локальному IP-адресу. Это снижает зависимость от внешних облачных сервисов и сохраняет данные внутри локальной инфраструктуры.

Для локальной системы часто достаточно встроенной базы данных. SQLite подходит для такого сценария, потому что не требует отдельного серверного процесса, хранит данные в одном файле и поддерживает стандартные SQL-операции. Для системы с одним локальным экземпляром, небольшим числом администраторов и умеренным объемом карточек событий такой вариант проще в установке и обслуживании, чем отдельная СУБД.

В проекте Kiosk_v001 эти принципы применяются следующим образом. Один Windows-компьютер запускает Flask-приложение через Waitress. Браузерные клиенты открывают маршруты `/kiosk`, `/kiosk/events`, `/tv`, `/preview` и `/admin`. Данные хранятся локально в SQLite, а runtime-файлы, включая базу данных, загруженные изображения и секретный ключ сессий, остаются вне собранного EXE-файла. Такая организация соответствует задаче локальной клиент-серверной системы: сервер централизует управление данными, а разные экраны получают актуальное представление этих данных.

## 2.2 Информационные киоски и Smart TV как средства отображения информации

Информационный киоск используется для предоставления сведений посетителю в понятной и доступной форме. Обычно такой экран размещается в общественной зоне и предполагает короткое взаимодействие: пользователь подходит к устройству, выбирает интересующий раздел, просматривает информацию и уходит. Поэтому интерфейс киоска должен быть простым, крупным и устойчивым к случайным действиям.

Smart TV или большой экран в режиме digital signage выполняет другую функцию. Он чаще используется как пассивное средство отображения: зритель не управляет интерфейсом, а воспринимает информацию с расстояния. Для такого режима важны читаемость, достаточная длительность показа слайда, контраст между изображением и текстом, а также понятное состояние, когда активных данных нет.

Различие между киоском и TV-экраном влияет на проектирование системы. Кiosk-экран может содержать кнопки, фильтры, переходы и действия пользователя. TV-режим должен быть более спокойным: автоматическая смена карточек, крупный заголовок, короткий текст и отсутствие лишних управляющих элементов. Если использовать один и тот же интерфейс для обоих режимов, он будет либо слишком пассивным для киоска, либо слишком перегруженным для TV.

Для публичных экранов важен полноэкранный режим. Он помогает скрыть лишние элементы браузера и сосредоточить внимание на содержании. Однако браузеры не позволяют надежно принудительно включать или блокировать fullscreen без участия пользователя, поэтому система должна использовать безопасные пользовательские сценарии: кнопку входа в полноэкранный режим и понятное поведение при попытке выхода через экранный интерфейс.

Также важны пустые состояния и поведение при бездействии. Если активных событий нет, экран не должен выглядеть сломанным или показывать незаполненную карточку. Он должен сообщать, что система готова и ожидает публикации данных. Для интерактивного киоска необходимо возвращение к стартовому экрану после длительного бездействия, потому что следующий посетитель должен увидеть начальное состояние, а не случайно оставленный фильтр или карточку.

Публичные экраны должны обновляться автоматически при изменении контента. Если администратор изменил событие, загрузил изображение или обновил настройки, экран киоска и TV должны получить актуальные данные без ручного обновления страницы оператором. Для этого в локальной системе может применяться периодическая проверка версии контента через API.

В Kiosk_v001 эти принципы отражены в разделении экранов. `/kiosk` выполняет роль стартовой страницы. `/kiosk/events` является интерактивным экраном с карточками событий и фильтрацией по тегам. `/tv` служит пассивным TV-режимом для большого экрана. `/preview` помогает администратору проверить, как публичные режимы выглядят перед использованием или во время настройки системы.

## 2.3 Проектирование пользовательских интерфейсов для публичных экранов

Интерфейс публичного экрана отличается от обычного интерфейса рабочего приложения. Пользователь может находиться на расстоянии, взаимодействовать с экраном короткое время или вообще не иметь клавиатуры и мыши. Поэтому основные требования к такому интерфейсу связаны с читаемостью, предсказуемостью и устойчивостью.

Текст на публичном экране должен быть достаточно крупным. Заголовок события, дата, место проведения и краткое описание должны восприниматься без напряжения. При этом длинные названия и описания не должны разрушать композицию экрана. Для этого применяются переносы строк, ограничение высоты текстовых блоков, разделение областей изображения и текста, а также разные макеты для интерактивного и пассивного режимов.

Навигация должна быть очевидной. На киоске посетитель должен понимать, как перейти к списку событий, выбрать тег, открыть следующую или предыдущую карточку и вернуться на главный экран. Управляющие элементы должны иметь достаточно крупную область нажатия и не должны требовать точных действий. Для TV-режима, наоборот, навигация обычно не нужна, потому что экран работает как автоматическая витрина.

Минимум отвлекающих элементов особенно важен для публичных экранов. Служебные индикаторы, версии контента, fullscreen-кнопки и другие элементы должны быть доступными, но не должны конкурировать с основной информацией. Если система показывает пустое состояние, оно должно быть спокойным и информативным, а не выглядеть как ошибка загрузки.

Поведение после бездействия является частью пользовательского интерфейса. В интерактивном режиме пользователь может оставить экран на конкретном событии или фильтре. Если следующий посетитель подойдет позже, ему удобнее начать со стартового экрана. Поэтому предупреждение о возврате и обратный отсчет позволяют совместить автоматический сброс состояния с возможностью продолжить просмотр при касании экрана.

Отдельного внимания требует баланс изображения и текста. Изображение помогает быстрее распознать событие, но не должно перекрывать название, дату или описание. В TV-режиме особенно важно отделять изображение от текстовой области, потому что наложенный на изображение текст может стать нечитаемым. В киоске допустим более карточный вид, где изображение является частью общей композиции события.

Административный интерфейс имеет другие задачи. Он предназначен не для посетителя, а для оператора, который создает, редактирует и проверяет данные. Поэтому admin UI должен быть более функциональным: формы, списки, кнопки действий, сообщения о результате операции, предварительный просмотр и настройки. При этом он не должен повторять публичный экран полностью; достаточно удобных preview-блоков, которые помогают понять будущий вид карточки.

Адаптивность интерфейса важна, потому что система может открываться на разных устройствах: большом киоске, TV-браузере, ноутбуке администратора или телефоне для проверки. Адаптивный дизайн не означает, что все экраны должны выглядеть одинаково. Он означает, что элементы не должны ломаться, выходить за границы, перекрывать друг друга или становиться нечитаемыми при изменении размера окна.

В Kiosk_v001 эти принципы применяются через карточки событий, фильтрацию по тегам, отдельный TV-макет с разделенными зонами изображения и текста, fullscreen-кнопки, предупреждение о бездействии на странице событий киоска, admin preview и интерфейсные переводы ru/en/de. При этом пользовательский контент событий и имена тегов не переводятся автоматически, потому что они вводятся администратором и должны отображаться в исходном виде.

## 2.4 Средства моделирования информационных систем

Проектирование информационной системы требует не только описания программного кода, но и представления функций, сценариев, структуры данных, архитектуры и алгоритмов в наглядной форме. Для этого используются разные нотации моделирования. Каждая нотация решает свою задачу и показывает систему с определенной стороны.

IDEF0 применяется для функционального моделирования. Такая диаграмма позволяет показать систему как набор функций, связанных входами, выходами, управляющими воздействиями и механизмами. Контекстная диаграмма A-0 полезна для общего описания Kiosk_v001 как системы управления и отображения событий. Диаграмма декомпозиции A0 может разделить общую функцию на процессы: управление событиями, обработку изображений, хранение данных, предоставление API, отображение на публичных экранах и запуск системы [в дальнейшем ссылка на диаграмму IDEF0].

UML Use Case диаграмма используется для описания акторов и вариантов использования. Для Kiosk_v001 такими акторами могут быть администратор, посетитель киоска, зритель TV-экрана и локальный оператор. Диаграмма вариантов использования позволяет показать, кто входит в административную панель, кто просматривает события, кто запускает сервер и какие действия доступны каждому участнику.

UML Sequence диаграммы помогают показать взаимодействие объектов и компонентов во времени. В курсовой работе целесообразно использовать sequence-диаграмму создания события: администратор отправляет форму, сервер обрабатывает данные, при необходимости создает версии изображения, сохраняет запись в SQLite и увеличивает версию контента. Вторая полезная sequence-диаграмма может описывать проверку обновлений через `/api/version`: клиентский экран периодически обращается к API, сравнивает версию и затем обновляет данные или страницу.

ER-диаграмма применяется для описания структуры базы данных. Для Kiosk_v001 она должна отразить сущности `users`, `events`, `tags`, `event_tags`, `settings` и `content_versions`. Особое внимание следует уделить связи многие-ко-многим между событиями и тегами через таблицу `event_tags`, а также хранению системных настроек и версии контента.

C4 Model используется для архитектурного описания системы на нескольких уровнях. Диаграмма System Context может показать Kiosk_v001 в окружении пользователей, браузеров, Smart TV, локальной сети и optional-клиента `ClientKiosk.exe`. Container diagram подходит для описания Flask/Waitress сервера, SQLite-базы, браузерных клиентов, статических файлов и внешних runtime-папок. Component diagram может детализировать серверное приложение: application factory, config, database, admin blueprint, API blueprint, image processing, i18n и startup helpers.

Блок-схемы по ГОСТ 19.701-90 / ISO 5807-85 подходят для описания алгоритмов. В рамках Kiosk_v001 их можно использовать для алгоритма запуска EXE/сервера, создания события, загрузки и обработки изображения, проверки `/api/version`, таймера бездействия на странице `/kiosk/events` и проверки текущих учетных данных администратора при защищенном выходе из полноэкранного режима.

Таким образом, набор диаграмм должен дополнять текстовую часть курсовой работы. IDEF0 показывает функции системы, UML описывает пользователей и взаимодействия, ER фиксирует структуру данных, C4 объясняет архитектуру, а блок-схемы раскрывают алгоритмы. Точные диаграммы будут размещены в приложениях после подготовки графических материалов.
