# Спецификации диаграмм для курсовой работы Kiosk_v001

## Назначение документа

Документ описывает состав и содержание диаграмм, которые будут подготовлены для приложений к курсовой работе по теме "Проектирование и разработка локальной информационной системы отображения событий для информационного киоска и Smart TV". Спецификации предназначены для последующего построения схем в графическом редакторе или CASE-средстве и помогают сохранить связь между диаграммами, текстом курсовой работы и фактической реализацией проекта Kiosk_v001.

Диаграммы должны отражать текущую архитектуру проекта: локальное Flask-приложение, SQLite-хранилище, административную панель, публичные экраны `/kiosk`, `/kiosk/events`, `/tv`, `/preview`, read-only API, обработку изображений, локальный LAN-запуск, EXE-сборку и внешние runtime-данные.

## 1 IDEF0 diagrams

### 1.1 Контекстная диаграмма IDEF0 A-0

Предлагаемое название: "Контекстная диаграмма функционирования системы Kiosk_v001".

Главный функциональный блок: "Управлять и отображать информацию о событиях".

Входы:

- данные событий;
- изображения событий;
- системные настройки;
- учетные данные администратора.

Управления:

- требования MVP;
- правила доступа администратора;
- требования локальной эксплуатации;
- требования к публичным экранам;
- стандарты проектирования и оформления.

Выходы:

- карточки событий на киоске;
- TV-отображение событий;
- экран предпросмотра;
- JSON API responses;
- сохраненные настройки и данные.

Механизмы:

- Flask application;
- SQLite database;
- Waitress server;
- browser clients;
- optional ClientKiosk.exe;
- PyInstaller EXE package;
- administrator/operator.

Примечания к построению:

- на диаграмме должен быть один центральный блок A-0;
- входы размещаются слева, управления сверху, механизмы снизу, выходы справа;
- подписи стрелок должны быть короткими и совпадать с терминологией курсовой работы;
- не следует показывать внутренние функции приложения на контекстной диаграмме.

### 1.2 Диаграмма декомпозиции IDEF0 A0

Предлагаемое название: "Декомпозиция основной функции системы Kiosk_v001".

Декомпозиция раскрывает центральную функцию "Управлять и отображать информацию о событиях" через шесть функциональных блоков.

| Блок | Название функции | Входы | Управления | Выходы | Механизмы |
| --- | --- | --- | --- | --- | --- |
| A1 | Управлять событиями и тегами | данные событий, учетные данные администратора, данные тегов | правила доступа администратора, требования MVP | сохраненные события, статусы событий, связи событий с тегами | admin feature module, browser, administrator |
| A2 | Обрабатывать изображения | загруженные изображения событий | требования к публичным экранам, правила хранения private/public файлов | private original, optimized kiosk image, optimized TV image, thumbnail | Pillow, image processing module, filesystem |
| A3 | Хранить данные и настройки | события, теги, настройки, пути изображений, учетные данные | схема SQLite, требования локальной эксплуатации | записи SQLite, content_version, сохраненные настройки | SQLite database, database helpers |
| A4 | Предоставлять публичный API | данные из SQLite, content_version | public API contract, фильтрация active events | JSON API responses для событий, тегов и версии | API blueprint, Flask route handlers |
| A5 | Отображать события на киоске и TV | API responses, настройки, шаблоны, static assets | требования к публичным экранам, interface_language, правила auto-update | `/kiosk`, `/kiosk/events`, `/tv`, `/preview` | browser clients, static JS, templates, optional ClientKiosk.exe |
| A6 | Запускать и обслуживать систему | CLI arguments, runtime paths, EXE/resources | требования локальной эксплуатации, LAN startup rules, password reset rules | работающий Waitress server, startup URLs, reset password output | serve.py, kiosk/server.py, Waitress, PyInstaller package, operator |

Связи между блоками:

- A6 создает условия выполнения приложения: запускает сервер, выводит локальные и LAN URL, при необходимости запускает внешний клиент или браузер.
- A1 передает данные событий и тегов в A3, а загруженные файлы изображений - в A2.
- A2 формирует пути к обработанным изображениям и передает их для сохранения в A3.
- A3 хранит данные, настройки и `content_version`, которые используются блоками A1, A4, A5 и A6.
- A4 читает данные из A3 и предоставляет их публичным клиентским экранам.
- A5 использует шаблоны, статические файлы, настройки и API responses для отображения информации на киоске, TV и preview-экране.
- Изменения в A1, A2 и A3 приводят к увеличению `content_version`, после чего A4 и A5 обеспечивают обновление клиентских экранов.

## 2 UML Use Case diagram

Предлагаемое название: "Диаграмма вариантов использования системы Kiosk_v001".

Актеры:

- Администратор;
- Посетитель киоска;
- Зритель TV-экрана;
- Локальный оператор.

Варианты использования администратора:

- войти в панель администратора;
- создать событие;
- редактировать событие;
- скрыть/показать событие;
- удалить событие;
- управлять тегами;
- назначить теги событию;
- загрузить изображение;
- изменить системные настройки;
- изменить пароль;
- открыть предпросмотр.

Варианты использования посетителя киоска:

- открыть главный экран киоска;
- просмотреть карточки событий;
- фильтровать события по тегам;
- вернуться на главный экран.

Варианты использования зрителя TV-экрана:

- просматривать события в TV-режиме.

Варианты использования локального оператора:

- запустить сервер/EXE;
- открыть страницу по LAN;
- сбросить пароль администратора через CLI.

Рекомендации по связям:

- "создать событие" и "редактировать событие" могут иметь связь `extend` с вариантом "загрузить изображение", так как изображение не является обязательным для каждого действия;
- "управлять тегами" может обобщать создание, изменение и удаление тегов, если диаграмма становится слишком перегруженной;
- "назначить теги событию" следует оставить отдельным вариантом, потому что он связывает события и теги;
- "открыть предпросмотр" относится к администратору и использует существующий маршрут `/preview`;
- не следует чрезмерно использовать `include` и `extend`, если они ухудшают читаемость.

Не включать в диаграмму:

- внутренние функции Python-модулей;
- таблицы базы данных;
- JavaScript-функции;
- детали обработки изображений;
- вспомогательные startup helpers.

## 3 UML Sequence diagrams

### 3.1 Sequence diagram: создание события

Название: "Диаграмма последовательности создания карточки события".

Участники:

- Администратор;
- Browser;
- Admin route;
- Image processing module;
- SQLite database;
- Content version.

Основной поток:

1. Администратор открывает форму создания события.
2. Browser отправляет `GET /admin/events/create`.
3. Admin route возвращает HTML-форму с полями события и предпросмотром.
4. Администратор заполняет заголовок, дату, место, краткое и полное описание, статус, порядок сортировки и при необходимости выбирает изображение.
5. Browser отправляет `POST /admin/events/create` с form data.
6. Admin route проверяет авторизацию администратора и валидирует входные данные.
7. Если изображение загружено, Admin route передает файл в Image processing module.
8. Image processing module сохраняет private original и создает optimized kiosk, TV и thumbnail outputs.
9. Image processing module возвращает пути к сохраненным файлам.
10. Admin route вставляет запись события в SQLite database.
11. Admin route вызывает увеличение Content version.
12. SQLite database сохраняет новую версию содержимого.
13. Browser получает redirect на список событий `/admin/events`.
14. Администратор видит обновленный список и flash-сообщение.

Альтернативная ветка "Изображение не загружено":

- шаги обработки изображения пропускаются;
- запись события сохраняется без путей к изображению;
- публичные и admin-preview экраны используют placeholder.

Альтернативная ветка "Ошибка валидации":

- Admin route не создает запись в базе;
- Browser получает форму с сообщением об ошибке;
- `content_version` не увеличивается.

### 3.2 Sequence diagram: проверка обновления через /api/version

Название: "Диаграмма последовательности проверки версии контента".

Участники:

- Kiosk/TV/Preview JS;
- `/api/version`;
- SQLite settings/content_version;
- `/api/events`;
- DOM/page.

Основной поток:

1. Kiosk/TV/Preview JS запускает polling timer после загрузки страницы.
2. JS отправляет запрос `GET /api/version`.
3. `/api/version` читает текущий `content_version` из SQLite settings/content_version.
4. Сервер возвращает JSON с текущей версией содержимого.
5. JS сравнивает полученную версию с сохраненной локальной версией.
6. Если версия не изменилась, страница продолжает показывать текущие данные.
7. Если версия изменилась, JS применяет случайную задержку 0-10 секунд.
8. Для `/kiosk/events` JS запрашивает актуальные данные через `/api/events` и обновляет DOM.
9. Для экранов, где безопаснее полная перезагрузка, JS выполняет delayed refresh.
10. DOM/page отображает актуальные данные.
11. JS сохраняет новую известную версию и продолжает polling.

Альтернативная ветка "Ошибка сети или API":

- JS сохраняет текущий экран без сброса данных;
- ошибка не должна ломать интерфейс;
- следующая проверка выполняется по очередному polling interval.

Альтернативная ветка "Нет активных событий":

- `/api/events` возвращает пустой список;
- соответствующий экран показывает предусмотренное empty state;
- polling `/api/version` продолжает работать.

## 4 ER diagram

Название: "ER-диаграмма базы данных SQLite".

Сущности и ключевые поля:

| Сущность | Поля |
| --- | --- |
| users | `id`, `username`, `password_hash`, `created_at`, `updated_at` |
| events | `id`, `title`, `short_description`, `full_description`, `event_date`, `place`, `status`, `sort_order`, `image_original`, `image_kiosk`, `image_tv`, `image_thumb`, `created_at`, `updated_at` |
| tags | `id`, `name`, `created_at`, `updated_at` |
| event_tags | `event_id`, `tag_id` |
| settings | `key`, `value`, `updated_at` |
| content_versions | `id`, `version`, `created_at` |

Связи:

- `users` используется для административной аутентификации;
- `events` и `tags` связаны отношением многие-ко-многим через таблицу `event_tags`;
- `event_tags.event_id` ссылается на `events.id`;
- `event_tags.tag_id` ссылается на `tags.id`;
- `settings` хранит системные параметры: название, язык интерфейса, текст главного экрана киоска, длительность TV-слайдов, site icon и другие настройки;
- `content_versions` поддерживает механизм проверки обновления клиентских экранов;
- поля изображений в `events` хранят пути к private original и public optimized outputs.

Примечания к построению:

- показать primary keys для всех сущностей;
- показать foreign keys в `event_tags`;
- показать many-to-many relationship между `events` и `tags`;
- `settings` можно отобразить как key-value сущность;
- перед финальным построением сверить точный состав полей с `kiosk/database.py`.

### 5.2 C4 Container diagram

Название: "C4 Container diagram для Kiosk_v001".

Контейнеры:

| Контейнер | Назначение | Технологии |
| --- | --- | --- |
| Flask/Waitress server | Обрабатывает HTTP routes, admin actions, API requests, templates и startup behavior | Python, Flask, Waitress |
| SQLite database | Хранит пользователей, события, теги, настройки и версии содержимого | SQLite |
| Templates/static assets | Формируют HTML, CSS и JavaScript для публичных и admin-экранов | Jinja templates, CSS, JavaScript |
| Browser clients | Открывают `/kiosk`, `/kiosk/events`, `/tv`, `/preview`, `/admin` | Web browser |
| Optional ClientKiosk.exe | Внешний полноэкранный kiosk client, если размещен рядом с server EXE | External executable |
| External runtime folder | Хранит SQLite database, private uploads, public optimized uploads и secret key | Filesystem |

Связи:

- Browser clients отправляют HTTP requests на Flask/Waitress server.
- Optional ClientKiosk.exe открывает локальный URL киоска, переданный через CLI-аргументы.
- Flask/Waitress server читает и записывает данные в SQLite database.
- Flask/Waitress server использует templates/static assets для формирования страниц.
- Flask/Waitress server сохраняет runtime data во external runtime folder.
- Templates/static assets содержат JS-клиенты, которые обращаются к `/api/version`, `/api/events` и `/api/tags`.
- External runtime folder остается вне EXE-бандла и должен сохраняться между запусками.

## 6 Flowcharts according to ГОСТ 19.701-90 / ISO 5807-85

### 6.1 Блок-схема запуска EXE/сервера

Название: "Блок-схема запуска EXE/сервера Kiosk_v001".

Начало:

- оператор запускает `python serve.py` или `Kiosk_v001.exe`.

Шаги:

1. Разобрать CLI arguments.
2. Проверить, выбран ли режим `--reset-admin-password`.
3. Если выбран reset password mode, открыть runtime database, сбросить пароль администратора, вывести temporary password и завершить программу.
4. Определить host и port.
5. Проверить, отвечает ли локальный сервер на `http://127.0.0.1:<port>/api/version`.
6. Если локальный сервер уже работает, не запускать второй сервер, а перейти к client/browser launch logic.
7. Если сервер не работает, создать Flask app и запустить Waitress server.
8. Вывести bound server URL, local URLs, LAN URLs и подсказки про VPN/Wi-Fi/Windows Firewall.
9. Проверить `--no-client`.
10. Если `--no-client` включен, пропустить запуск ClientKiosk.exe и browser fallback.
11. Если auto-launch включен, выполнить поиск `ClientKiosk.exe`.
12. Если `ClientKiosk.exe` найден, запустить его с URL, host, port и mode.
13. Если `ClientKiosk.exe` не найден или запуск не удался, попробовать default browser fallback.
14. Если browser fallback не удался, вывести manual URL.
15. Сервер продолжает работать до остановки оператором.

Точки решений:

- `--reset-admin-password` указан?
- локальный сервер уже отвечает?
- `--no-client` указан?
- `ClientKiosk.exe` найден?
- запуск `ClientKiosk.exe` успешен?
- browser fallback успешен?

Выходы:

- работающий Waitress server;
- список URL для локального и LAN-доступа;
- запущенный внешний клиент или браузер, если доступно;
- manual URL при невозможности открыть клиент автоматически.

Конец:

- для reset password mode программа завершается после вывода temporary password;
- для server mode процесс работает до ручной остановки.

Примечания к построению:

- использовать терминатор "Начало/Конец", процессные блоки, блоки решения и блоки вывода;
- не показывать внутреннюю реализацию Waitress;
- отдельно отразить ветку `--no-client`.

### 6.2 Блок-схема создания события

Название: "Блок-схема создания события в административной панели".

Начало:

- администратор вошел в систему и открыл `/admin/events/create`.

Шаги:

1. Открыть форму создания события.
2. Ввести title, event_date, place, short_description, full_description, status и sort_order.
3. При необходимости выбрать image file.
4. Отправить форму.
5. Проверить авторизацию администратора.
6. Валидировать обязательные поля.
7. Проверить, загружено ли изображение.
8. Если изображение загружено, выполнить обработку изображения.
9. Сохранить событие в SQLite.
10. Увеличить `content_version`.
11. Показать flash message.
12. Перенаправить на `/admin/events`.

Точки решений:

- администратор авторизован?
- данные формы валидны?
- изображение загружено?
- обработка изображения успешна?

Выходы:

- новая запись события;
- пути изображений, если файл был загружен;
- увеличенная версия содержимого;
- обновленный список событий в admin panel.

Конец:

- событие создано или форма возвращена с ошибкой.

### 6.3 Блок-схема загрузки и обработки изображения

Название: "Блок-схема загрузки и обработки изображения события".

Начало:

- admin route получил image file из формы события.

Шаги:

1. Получить файл изображения.
2. Проверить наличие файла.
3. Проверить допустимость и читаемость изображения.
4. Сформировать безопасное имя файла.
5. Сохранить private original.
6. Создать optimized kiosk image.
7. Создать optimized TV image.
8. Создать thumbnail.
9. Сформировать пути для записи события.
10. Вернуть пути в admin route.

Точки решений:

- файл передан?
- файл является корректным изображением?
- удалось сохранить original?
- удалось создать optimized outputs?

Выходы:

- private original path;
- public kiosk image path;
- public TV image path;
- public thumbnail path;
- безопасный fallback при отсутствии или ошибке файла.

Конец:

- admin route получает результат обработки или продолжает сохранение без изображения.

Примечания к построению:

- private original и public optimized outputs следует показать как разные ветви хранения;
- не нужно показывать конкретные размеры изображений, если это перегружает блок-схему.

### 6.4 Блок-схема проверки /api/version

Название: "Блок-схема проверки версии содержимого клиентским экраном".

Начало:

- клиентская страница `/kiosk`, `/kiosk/events`, `/tv` или `/preview` загружена.

Шаги:

1. Запустить polling timer.
2. Отправить запрос `GET /api/version`.
3. Получить текущий `content_version`.
4. Сравнить полученную версию с сохраненной локальной версией.
5. Если версия не изменилась, продолжить показ текущего экрана.
6. Если версия изменилась, выбрать случайную задержку 0-10 секунд.
7. После задержки запросить данные или обновить страницу в зависимости от типа экрана.
8. Обновить stored version.
9. Продолжить polling.

Точки решений:

- запрос `/api/version` успешен?
- версия изменилась?
- текущий экран поддерживает частичное обновление данных?

Выходы:

- обновленный DOM или перезагруженная страница;
- сохраненная новая версия;
- сохранение текущего экрана при ошибке.

Конец:

- цикл не имеет обычного завершения и продолжается до закрытия страницы.

### 6.5 Блок-схема таймера бездействия киоска

Название: "Блок-схема таймера бездействия на странице событий киоска".

Начало:

- пользователь открыл `/kiosk/events`.

Шаги:

1. Запустить inactivity timer на 120 секунд.
2. Отслеживать действия пользователя: touch, click, pointer или keyboard activity.
3. Если действие пользователя произошло до истечения 120 секунд, сбросить inactivity timer.
4. Если 120 секунд истекли, показать warning overlay.
5. Запустить countdown на 30 секунд.
6. Обновлять число countdown каждую секунду.
7. Если пользователь проявил активность во время warning, скрыть warning и сбросить inactivity timer.
8. Если countdown дошел до нуля, перенаправить на `/kiosk`.

Точки решений:

- была ли активность пользователя?
- истекли ли 120 секунд?
- warning уже отображается?
- countdown достиг нуля?

Выходы:

- скрытое или отображенное предупреждение;
- сброшенный timer при активности;
- redirect на `/kiosk` при отсутствии активности.

Конец:

- пользователь возвращен на главный экран или продолжает просмотр после активности.

### 6.6 Блок-схема входа администратора и fullscreen unlock

Название: "Блок-схема проверки учетных данных администратора".

Начало:

- пользователь вводит username и password в `/admin/login` или в fullscreen unlock modal на `/kiosk`.

Шаги:

1. Получить username и password.
2. Найти пользователя в таблице `users`.
3. Проверить password hash.
4. Определить контекст проверки: обычный login route или fullscreen validate route.
5. Если учетные данные верны и это login route, создать admin session и перенаправить на `/admin`.
6. Если учетные данные верны и это fullscreen validate route, вернуть JSON `{"success": true}`.
7. Если учетные данные неверны и это login route, вернуть ошибку входа без создания session.
8. Если учетные данные неверны и это fullscreen validate route, вернуть JSON `{"success": false}`.

Точки решений:

- пользователь найден?
- password hash прошел проверку?
- запрос относится к login route?
- запрос относится к fullscreen validate route?

Выходы:

- admin session и redirect при успешном обычном входе;
- JSON success/failure для fullscreen unlock;
- ошибка входа при неверных данных.

Ограничения безопасности:

- не возвращать `password_hash`;
- не возвращать plaintext password;
- не сообщать отдельно, неверен логин или пароль;
- не хранить пароль в JavaScript;
- fullscreen unlock использует текущие учетные данные администратора, а не отдельный пароль.

Конец:

- пользователь вошел в admin panel, получил отказ или получил разрешение/отказ на выход из fullscreen.
