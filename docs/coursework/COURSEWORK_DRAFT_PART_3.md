# Черновик курсовой работы. Глава 3

## 3 Практическая часть

В практической части рассматривается проектирование и реализация программного продукта Kiosk_v001. Система представляет собой локальное клиент-серверное приложение для управления карточками событий и их отображения на информационном киоске, Smart TV, экране предпросмотра и в административной панели. В данной главе описываются структура системы, основные программные модули, организация хранения данных, пользовательский интерфейс, механизм обновления клиентских экранов, сборка исполняемого файла и подход к тестированию.

## 3.1 Анализ задачи

Практическая задача, решаемая системой Kiosk_v001, заключается в создании локального программного комплекса, который позволяет администратору быстро публиковать сведения о событиях и автоматически показывать их на публичных экранах. Такая система должна работать в пределах локального компьютера или локальной сети, не требовать обязательного размещения в интернете и сохранять все рабочие данные в локальном runtime-каталоге.

В системе выделяются несколько типов участников. Администратор управляет содержимым: выполняет вход в административную панель, создаёт и редактирует карточки событий, скрывает или показывает события, назначает теги, загружает изображения и изменяет системные настройки. Посетитель киоска использует публичный интерактивный экран, переходит к списку событий, просматривает карточки и применяет фильтрацию по тегам. Зритель TV-экрана не взаимодействует с системой напрямую, а воспринимает автоматическую демонстрацию активных событий. Локальный оператор отвечает за запуск сервера или исполняемого файла, проверку доступности страниц и, при необходимости, сброс пароля администратора.

Основные сценарии работы включают запуск приложения через `serve.py` или собранный `Kiosk_v001.exe`, вход администратора в панель управления, создание и редактирование событий, назначение тегов и загрузку изображений. После сохранения данных публичные клиенты получают обновления через механизм проверки `/api/version`. Посетитель открывает `/kiosk/events` и просматривает активные карточки, а TV-экран открывает `/tv` и автоматически переключает события. Для документации проекта в приложениях планируется разместить диаграмму вариантов использования и IDEF0-диаграммы, отражающие верхнеуровневую функцию системы и её декомпозицию.

## 3.2 Описание логической структуры системы

Логическая структура Kiosk_v001 разделена на несколько подсистем. Подсистема запуска и runtime-конфигурации отвечает за выбор режима запуска, настройку host/port, работу LAN-доступа, создание внешних runtime-каталогов и загрузку постоянного секретного ключа Flask. Административная панель обеспечивает авторизацию администратора, управление событиями, тегами, настройками, изображениями и паролем. Публичные экраны отображают данные для посетителей и зрителей: стартовую страницу киоска, список событий, TV-режим и страницу предпросмотра.

Отдельную роль выполняет публичный API. Он предоставляет только чтение данных, необходимых клиентским экранам: текущую версию содержимого, список активных событий, отдельное активное событие и список тегов. Подсистема хранения данных использует SQLite и содержит таблицы для пользователей, событий, тегов, связей между событиями и тегами, настроек и истории версий содержимого. Подсистема обработки изображений сохраняет исходные файлы отдельно от публичных оптимизированных версий. Подсистема интернационализации обеспечивает интерфейсные переводы для русского, английского и немецкого языков.

Основными маршрутами приложения являются `/kiosk`, `/kiosk/events`, `/tv`, `/preview`, `/admin`, `/api/version`, `/api/events` и `/api/tags`. Маршрут `/kiosk` открывает стартовый экран киоска, `/kiosk/events` показывает интерактивные карточки событий, `/tv` используется для пассивного TV-отображения, `/preview` служит для проверки публичных экранов, `/admin` открывает административную панель, а маршруты `/api/...` используются клиентскими скриптами для обновления данных.

Главные сущности базы данных: `users`, `events`, `tags`, `event_tags`, `settings` и `content_versions`. Таблица `users` хранит учётную запись администратора и хэш пароля. Таблица `events` хранит карточки событий. Таблица `tags` содержит теги, а `event_tags` связывает события с тегами. Таблица `settings` хранит системные настройки, включая заголовок, язык интерфейса, тексты стартовой страницы киоска, иконку и текущий `content_version`. Таблица `content_versions` фиксирует изменения версии содержимого. ER-диаграмма базы данных будет размещена в приложениях [в дальнейшем ссылка на ER-диаграмму].

## 3.3 Архитектура программного решения

Kiosk_v001 реализован как модульное монолитное приложение на Flask. Такой подход подходит для локальной информационной системы, поскольку все основные функции находятся в одном развёртываемом приложении, но при этом код разделён по зонам ответственности. Приложение создаётся через фабрику Flask, после чего регистрируются административный и API-модули, подключаются шаблоны, статические файлы, конфигурация и база данных.

Административный модуль отвечает за защищённые пользовательские операции: вход администратора, управление событиями, тегами, настройками, паролем и проверку учётных данных для выхода из полноэкранного режима киоска. API-модуль предоставляет публичные read-only-эндпоинты для клиентских экранов. Слой базы данных инкапсулирует подключение к SQLite, создание схемы и вспомогательные операции обновления версии содержимого. Модуль обработки изображений формирует оптимизированные версии файлов, а модуль i18n загружает переводы из JSON-файлов.

Производственный запуск выполняется через Waitress и `serve.py`. Этот режим рассчитан на локальную сеть: по умолчанию сервер доступен на `0.0.0.0`, а локальный клиент или браузер открывает адрес `127.0.0.1`. Для распространения на Windows используется PyInstaller и спецификация `Kiosk_v001.spec`. Runtime-данные, включая SQLite-базу, секретный ключ, загруженные файлы и служебные данные, остаются вне исполняемого набора файлов, что позволяет обновлять программу без обязательной потери пользовательских данных.

Архитектура является достаточной для локальной системы киоска: она не требует отдельного сервера баз данных, не зависит от облачной инфраструктуры и может запускаться на одном Windows-компьютере. В приложениях планируется представить C4-диаграммы уровней System Context, Container и Component, чтобы показать место системы в окружении, основные контейнеры и внутренние компоненты Flask-приложения.

## 3.4 Разработка программных модулей

Файл `run.py` предназначен для локального режима разработки. Он создаёт Flask-приложение и запускает встроенный сервер разработки с локальными настройками. В отличие от производственного режима, этот запуск не предназначен для штатной работы в локальной сети.

Файл `serve.py` реализует CLI для производственного и EXE-запуска. Через него доступны параметры host и port, отключение автоматического запуска клиента через `--no-client`, запуск страниц киоска или TV, а также команда сброса пароля администратора. Модуль `kiosk/server.py` содержит вспомогательную логику Waitress-запуска, вывод локальных и LAN-адресов, проверку уже запущенного локального сервера, поиск внешнего `ClientKiosk.exe` и fallback-открытие страницы в браузере.

Файл `kiosk/app.py` создаёт приложение Flask, регистрирует blueprint-модули, настраивает шаблоны и маршруты публичных экранов. Конфигурация находится в `kiosk/config.py`: там определены пути к ресурсам, runtime-каталогам, базе данных, upload-директориям и постоянному секретному ключу с поддержкой переменной окружения `KIOSK_SECRET_KEY`. Файл `kiosk/database.py` отвечает за подключение к SQLite, создание таблиц, начальные настройки и увеличение версии содержимого.

Модуль `kiosk/core/images.py` обрабатывает изображения событий и системную иконку. Он сохраняет исходные файлы в закрытой области и создаёт публичные оптимизированные версии для киоска, TV и миниатюр. Модуль `kiosk/core/i18n.py` загружает JSON-переводы и возвращает локализованные интерфейсные строки.

Файл `kiosk/features/admin/routes.py` содержит маршруты административной панели: авторизацию, управление событиями, тегами, настройками, изображениями, паролем и проверку учётных данных для защищённого выхода из полноэкранного режима киоска. Файл `kiosk/features/api/routes.py` содержит публичный API для версии содержимого, событий и тегов.

На стороне клиента используются отдельные JavaScript-файлы. `kiosk/static/js/kiosk_home.js` управляет стартовой страницей киоска, полноэкранным режимом и модальным окном разблокировки выхода. `kiosk/static/js/kiosk_events.js` отвечает за список событий, навигацию, фильтрацию по тегам, обновление через API и предупреждение о неактивности. `kiosk/static/js/tv.js` реализует TV-слайдшоу, полноэкранную кнопку, обработку пустого состояния, проверку версии и расчёт длительности показа слайда. Подробные фрагменты ключевых файлов будут приведены в приложении Д.

## 3.5 Организация хранения данных

Для хранения данных используется SQLite. В рабочем режиме база располагается во внешнем runtime-каталоге, например в `instance/kiosk.sqlite`, а не внутри собранного исполняемого набора. Такой подход позволяет сохранять пользовательские данные при перезапуске и обновлении программы. Runtime-данные также включают файл постоянного секретного ключа `instance/secret_key.txt` и загруженные изображения.

База данных содержит таблицы `users`, `events`, `tags`, `event_tags`, `settings` и `content_versions`. В таблице `users` хранится администратор и хэш его пароля. Пароль не сохраняется в открытом виде. Таблица `events` содержит данные карточек: `title`, `short_description`, `full_description`, `event_date`, `place`, `status`, `sort_order`, а также пути к изображениям. Статус события принимает значения `active` или `hidden`, что позволяет управлять видимостью карточки в публичном API без удаления записи.

Таблица `tags` хранит пользовательские теги, а `event_tags` реализует связь многие-ко-многим между событиями и тегами. Таблица `settings` используется для системного заголовка, языка интерфейса, иконки, текстов стартовой страницы киоска, длительности TV-слайдов и текущей версии содержимого. При изменении событий, тегов, настроек, изображений или иконки значение `content_version` увеличивается. Клиентские экраны используют эту версию для определения необходимости обновления.

Изображения событий хранятся в двух логических областях. Исходный файл сохраняется как private original и не предназначен для прямой публичной отдачи. Для интерфейсов формируются оптимизированные публичные версии: kiosk, tv и thumb. Это уменьшает объём передаваемых данных и позволяет использовать разные размеры изображения для разных экранов. Шифрование данных в системе не заявляется; безопасность административной сессии обеспечивается хэшированием пароля и постоянным runtime-секретом Flask.

## 3.6 Реализация пользовательского интерфейса

Пользовательский интерфейс разделён на публичные экраны и административную часть. Страница `/kiosk` является стартовым экраном киоска. Она показывает название системы, настраиваемые текстовые блоки и переход к просмотру событий. На этой странице предусмотрена полноэкранная кнопка, а выход из полноэкранного режима через публичную кнопку защищён текущими учётными данными администратора.

Страница `/kiosk/events` предназначена для интерактивного просмотра событий. Она отображает активные карточки, кнопки навигации, счётчик текущей карточки, фильтрацию по тегам и модальное окно всех тегов. При длительной неактивности появляется предупреждение с 30-секундным обратным отсчётом, после чего экран возвращается на `/kiosk`. Это важно для публичного киоска, так как после взаимодействия посетителя экран должен самостоятельно возвращаться в исходное состояние.

Страница `/tv` реализует пассивный режим отображения. Для неё используется отдельная композиция: изображение и текстовая панель разделены, заголовок и краткая информация должны быть читаемы с расстояния. При отсутствии активных событий показывается спокойное пустое состояние. TV-страница содержит ненавязчивую полноэкранную кнопку и автоматически проверяет обновления содержимого.

Страница `/preview` используется для административной проверки публичных экранов. Административные страницы включают `/admin/login`, `/admin`, `/admin/events`, `/admin/events/create`, `/admin/tags`, `/admin/settings` и `/admin/password/change`. В панели администратора доступны ссылки на управление данными и на предпросмотр. Формы событий содержат preview-блоки для киоск- и TV-представления, что позволяет оценить внешний вид карточки до проверки на публичном экране.

Интерфейс поддерживает русский, английский и немецкий языки для системных подписей. При этом пользовательские данные, такие как названия событий, описания, места и имена тегов, не переводятся автоматически и отображаются так, как были введены администратором. CSS-стили обеспечивают адаптивность страниц, читаемые пустые состояния, единое оформление карточек, flash-сообщения в админке и разделение визуального поведения публичных экранов. Скриншоты основных экранов будут размещены в приложении А [в дальнейшем ссылка на скриншоты интерфейса].

## 3.7 Реализация обновления клиентских экранов

Для обновления клиентских экранов используется endpoint `/api/version`. Он возвращает текущее значение `content_version`, которое хранится в настройках системы. Версия увеличивается при изменении событий, тегов, настроек, изображений и системной иконки. Такой механизм позволяет клиентским страницам не загружать все данные постоянно, а сначала проверять, изменилась ли версия содержимого.

Страницы `/kiosk`, `/kiosk/events`, `/tv` и `/preview` периодически обращаются к `/api/version`. Если обнаружена новая версия, обновление применяется с случайной задержкой от 0 до 10 секунд. Эта задержка снижает вероятность одновременного обновления всех открытых экранов в один момент, что особенно полезно при работе нескольких клиентов в локальной сети.

На странице `/kiosk/events` после изменения версии данные событий и тегов могут обновляться через API без полной перезагрузки страницы. Фильтрация по тегам выполняется на клиентской стороне с использованием тегов, которые уже присутствуют в объектах событий из `/api/events`. При смене фильтра текущий индекс карточки безопасно сбрасывается, а навигация назад и вперёд продолжает работать с отфильтрованным списком.

В TV-режиме используется безопасное обновление с сохранением логики слайд-шоу. Длительность показа слайда зависит от базовой настройки и объёма текста события: более длинные заголовки, описания и места остаются на экране дольше, но в пределах разумных ограничений. Если активных событий нет, вместо растянутой пустой карточки показывается отдельное пустое состояние.

Для интерактивного киоска реализован таймер неактивности. После 120 секунд без действий появляется предупреждение, затем начинается 30-секундный обратный отсчёт. Любое касание, клик или другое поддерживаемое действие скрывает предупреждение и сбрасывает таймер. Если отсчёт доходит до нуля, выполняется переход на `/kiosk`. Последовательность проверки версии и алгоритм таймера будут дополнительно представлены в виде sequence-диаграммы и блок-схемы.

## 3.8 Сборка исполняемого файла

Для эксплуатации на Windows предусмотрена сборка исполняемого набора файлов. Такой вариант удобен для оператора: приложение можно запускать как обычную программу, не выполняя вручную команды Python. Сборка выполняется с помощью PyInstaller по спецификации `Kiosk_v001.spec`.

Результат сборки размещается в каталоге `dist/Kiosk_v001/`, где находится `Kiosk_v001.exe` и необходимые файлы приложения. В набор включаются шаблоны, статические файлы и переводы. При этом рабочие runtime-данные остаются внешними: `instance/kiosk.sqlite`, `instance/secret_key.txt`, загруженные файлы и upload-каталоги располагаются рядом с исполняемым приложением и не должны удаляться, если требуется сохранить данные.

Обычный производственный запуск по умолчанию использует host `0.0.0.0`, что делает сервер доступным в локальной сети. Для локального режима доступен параметр `--host 127.0.0.1`. Параметр `--no-client` отключает автоматический запуск внешнего клиента или браузера, а `--reset-admin-password` выполняет сброс пароля администратора и выводит временный пароль.

Если рядом с серверным EXE находится внешний `ClientKiosk.exe`, сервер пытается запустить его автоматически и передаёт параметры URL, host, port и mode. Если `ClientKiosk.exe` отсутствует или не запускается, используется fallback-открытие страницы киоска в браузере. Если и браузер открыть не удалось, сервер продолжает работать и выводит URL для ручного открытия. Для доступа с телефона, планшета или Smart TV устройство должно находиться в той же сети, а Windows Firewall должен разрешать входящие подключения на выбранный TCP-порт. При проблемах с подключением также необходимо учитывать VPN и Wi-Fi-сегментацию.

## 3.9 Тестирование программного продукта

Проверка Kiosk_v001 выполняется сочетанием ручного тестирования и автоматизированных regression smoke tests. Ручные проверки применяются для визуального контроля публичных экранов, полноэкранного режима, удобства административной панели и работы в локальной сети. Автоматические проверки расположены в `tests/test_mvp_smoke.py` и запускаются командой:

```text
python -m unittest discover -s tests
```

Тесты используют временную SQLite-базу и временные upload-каталоги, поэтому не должны затрагивать реальный файл `instance/kiosk.sqlite`. Такой подход позволяет проверять сценарии создания данных, загрузки изображений и изменения настроек без риска повредить рабочую базу.

Автоматические тесты покрывают доступность основных маршрутов, авторизацию администратора, видимость активных и скрытых событий в API, работу тегов, сохранение настроек, увеличение `content_version`, обработку изображений и системной иконки, защищённую проверку выхода из полноэкранного режима, helpers запуска, постоянный runtime-секрет и ключевые элементы интерфейсной разметки. Также проверяется, что API отдаёт активные события с назначенными тегами, а старые или скрытые данные не попадают в публичный список.

План ручных тест-кейсов подготовлен отдельно и будет использован для приложения В. В него входят проверки входа администратора, создания и редактирования события, скрытия и показа события, управления тегами, загрузки изображений, сохранения настроек, отображения киоска и TV, работы `/api/version`, защищённого выхода из fullscreen, LAN-запуска, EXE-запуска и сброса пароля администратора.

## 3.10 Эксплуатационная документация

В режиме разработки приложение запускается командой:

```text
python run.py
```

Этот режим предназначен для локальной разработки и проверки. Для производственного запуска через Waitress используется команда:

```text
python serve.py
```

Собранное приложение запускается через:

```text
dist/Kiosk_v001/Kiosk_v001.exe
```

По умолчанию производственный запуск доступен в локальной сети. На компьютере можно открыть локальные адреса `http://127.0.0.1:5000/kiosk`, `http://127.0.0.1:5000/kiosk/events`, `http://127.0.0.1:5000/tv`, `http://127.0.0.1:5000/preview` и `http://127.0.0.1:5000/admin/login`. Для смартфона, планшета или Smart TV используется адрес компьютера в локальной сети, например `http://<computer-lan-ip>:5000/tv`.

Администратор входит через `/admin/login`, после чего может создавать и редактировать события, назначать теги, загружать изображения, изменять системные настройки, менять пароль и открывать страницу предпросмотра. Если пароль администратора утрачен, сброс выполняется через CLI:

```text
python serve.py --reset-admin-password
```

или для собранного приложения:

```text
Kiosk_v001.exe --reset-admin-password
```

Для локального-only режима сервер можно запустить с параметром `--host 127.0.0.1`. Для отключения автоматического запуска внешнего клиента или браузера используется `--no-client`. Если приложение должно стартовать вместе с Windows, оператор может добавить ярлык `Kiosk_v001.exe` в папку автозагрузки Windows. При эксплуатации важно сохранять runtime-каталог и не удалять `instance/kiosk.sqlite`, если требуется сохранить события, теги, настройки и учётные данные.
